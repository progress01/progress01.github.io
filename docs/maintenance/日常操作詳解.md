# 日常操作詳解

日常更新先看[網站維護更新手冊](../../網站維護更新手冊.md)。這份文件保留完整操作細節，遇到特定欄位或問題時再查詢；以下程式碼中的檔案路徑均相對於專案根目錄。Windows PowerShell 可將指令中的 `npm`／`npx` 寫成 `npm.cmd`／`npx.cmd`。

## 哪份才是工作中的資料

固定在 `D:\myblog1988\blog-1988` 操作，Typora 開這裡的 `source/_posts/` 文章。這是目前工作的版本，可能包含尚未提交或發布的修改，不能只憑檔案存在就認定已備份或已上線。

| 位置 | 用途 |
| --- | --- |
| `blog-1988/source/` | 正在編輯的原始資料；文章在 `_posts/`，圖片在 `images/` |
| GitHub 的 `source` 分支 | 已推送的原始資料備份；本機存檔或 commit 不等於已推送 |
| `blog-1988/public/` | 自動生成的預覽／發布候選，可以重建，不在這裡改文章 |
| `blog-1988/.deploy_git/` 與 GitHub 的 `main` 分支 | 發布工具使用的生成網站；不作為文章編輯來源 |
| `blog-migration-2026-10-08/`、`cleanup-backup-20261013/` | 搬機與清理時的歷史備份，不是日常更新目錄 |

一般改文不用另寫進度表、review 文件或發布驗收報告，也不用更新正文雜湊。文章版本由 Git 保存；每次完成只需簡短交代「改了什麼、原始資料是否已推送、網站是否已上線、是否還有問題」。沒有查過的狀態寫未確認，不用再為交付紀錄額外發布一次。

畫面與閱讀感受由作者驗收；代理負責程式、資料同步、文章／圖片連結、既有功能、發布流程與來源備份。代理沒有可用瀏覽器時仍繼續其餘檢查，不把畫面標記為已通過，也不為此反覆重跑整站測試。部署仍依作者的明確指示執行。

## 先記住三件事

1. 編輯原始資料：`source/`。
2. 要發布目前整站時執行 `npm run publish -- --execute`，它會一起完成檢查、備份與部署。
3. 不要手動修改 `public/`、`calendar.json` 或 `calendar-posts.json`。

`public/` 是 Hexo 建置後自動產生的網站檔案。直接修改它，下一次建置就會被覆蓋。

## 每次開始前

如果有使用 Git，先在專案資料夾開啟 PowerShell，確認目前是否有別人的修改：

```powershell
git status --short
```

看到原本就存在的修改時，不要為了整理畫面而重設或覆蓋它們。日常內容更新通常只需要改一個或幾個 `source` 檔案。

## 新增一篇文章

### 1. 建立檔案

在專案資料夾執行：

```powershell
npx hexo new post "文章標題"
```

檔案會出現在 `source/_posts/`。如果是自己用資料夾整理的文章，可以放進既有的分類資料夾；已經發布的文章不要任意改檔名或搬資料夾，以免網址改變。

新文章一律先放 B 面（個人記憶庫），範本已自動填入 `surfaces: [memory]`，草稿也相同。先記錄、先發布，之後慢慢整理；不需要每篇重新決定放哪一面。

### 2. 填寫文章開頭

文章開頭的 front matter 建議維持這個格式：

```yaml
---
title: 文章標題
date: 2026-08-27 12:00:00
categories: [閱讀與影視]
tags: [閱讀心得]
surfaces: [memory]
---
```

如果是書籍或影視文章，想讓首頁使用統一的作品資料卡，可以再加入既有圖片的路徑：

```yaml
cover: /images/book_作品名稱.png
```

這只控制首頁的呈現，不會改變文章標題或正文。圖片必須真的存在於 `source/images/`，`npm run check:content` 會一起檢查。

公開分類以 `source/_data/content-categories.yml` 為準，目前為：

- `音樂`
- `閱讀與影視`
- `觀念與實驗`
- `工作知識`
- `生活紀錄`

`站務` 是內部網站紀錄用分類，不會出現在一般內容入口、搜尋分類按鈕和隨機文章篩選中。

分類名稱要完全相同，包含文字和標點。不要自行寫成「閱讀」、「電影」或「音樂推薦」，除非先把它加入分類設定。

### 3. 更新整站

```powershell
npm run publish -- --execute
```

`npm run check:content` 會以真正的 YAML 解析 front matter 與資料設定，檢查標題、日期是否為真實日曆日期、`updated` 是否不早於 `date`、分類與圖片路徑。它也會檢查 `source/reading-desk.yml` 的 topics/items 形狀、唯一 ID、`/learning/` 路徑、狀態值與日期關係，並把未註冊標籤逐篇列為 warning。

主標籤的 canonical 名稱只登記在 `source/_data/content-tags.yml`；同檔案的 `aliases` 供歷史標籤正規化。標籤可先留空；有填時最多兩個，不重複且須已登錄，未登錄標籤會被日常標籤檢查攔下。只想檢查、不上線時才執行 `npm run verify`。

文章的發表 `date` 由作者指定，也可以預先填寫未來的發表日期；它會同時影響文章排序、生活索引和文章發表熱力圖。`updated` 只記錄最後修訂，不會另造熱力圖事件，不需要另外填寫熱力圖資料。

### 新文章與既有文章的窄幅修改

- 新文章填寫 `title`、真實日曆 `date`、已註冊 `categories`，保留預設的 `surfaces: [memory]`。標籤可留空，有填時使用 `source/_data/content-tags.yml` 的 canonical 主標籤。
- 修改既有文章時，先保留原本的 `date`、`permalink`、無關 metadata 與正文；只改使用者指定的內容。只有實質內容修改才加入可靠的 `updated`，並使用 `Asia/Taipei` 時區；格式整理或圖片轉檔不新增 `updated`。
- 文章的標題、日期、作者、語言與頁面可見內容應保持一致；JSON-LD 由模板產生，規則與驗證方式見《Schema.org JSON-LD 實作手冊》。

### 整理好後加入 A 面

等作者確認要放到 A 面（工作與學習）時，只修改同一篇文章：

```yaml
surfaces: [profile, memory]
```

這樣會加入 A 面，同時保留 B 面紀錄；正文和網址都是原來那一份，不需要搬檔或複製文章。分類、標籤、是否寫完與 `thinking_status` 都不會自動把文章加入 A 面。

日常記錄不必填寫 `thinking_status`、`thinking_updated`、`thinking_boundary`。需要呈現探索中狀態時，再參考 [內容欄位規格](../dual-surface-content-contract.md) 的選填說明。

## 更新「碎碎念」

碎碎念會出現在生活索引和「碎碎念」頁面。新增時可直接執行：

```powershell
npm run record -- microblog --text "今天想記下的事"
```

工具自動填入台北今日、💭 標籤、B 面與穩定 ID，新紀錄放最上方。可選填 `--date "2026-10-15"`、`--tag "📚"`；只想預覽時加 `--dry-run`。這一步只改本機資料，不發布，也不必再跑補 ID 指令。寫入前的原檔保存在 `node_modules/.cache/record-backups/`，長期備份仍以推送至 GitHub 的 source 為準。

修改既有紀錄或手動新增時，只編輯：

```text
source/microblog.json
```

把新資料放在陣列最前面，格式如下：

```json
{
  "date": "2026-08-27",
  "tag": "💭",
  "content": "今天突然想到一件想記下來的事。",
  "surfaces": ["memory"]
}
```

注意：

- 日期使用 `YYYY-MM-DD`。
- `tag` 可以使用 emoji 或簡短文字。
- 一般內容直接寫文字即可。
- `surfaces` 指定公開位置：`["memory"]` 為生活面、`["profile"]` 為工作與學習面，也可同時填兩者。
- 手動新增後先執行 `node tools/assign-microblog-ids.js` 預覽，再執行 `node tools/assign-microblog-ids.js --write` 補齊新 ID；使用 `record` 指令新增時不用補 ID。修改或排序既有紀錄時保留原本的 `id`。
- 一般舊碎碎念可修改文字、日期、標籤與排列順序。曾經做過隱私清理的兩筆保留核准文字與欄位；已停用 ID 和已清除的私人原文仍不得重新加入。
- 如果真的要放連結，才使用 HTML，並保留 `target="_blank" rel="noopener noreferrer"`。
- 最後一筆資料後面不能多逗號；每筆資料之間要有逗號。
- 不要為了更新碎碎念去改 `source/status/index.md` 或首頁版型。

## 更新「現在的我」

首頁上方的「現在的我」資料在：

```text
source/life-index.json
```

通常只需要修改 `current.listen` 或 `current.watch` 裡的文字和連結。例如：

```json
"listen": {
  "label": "LISTEN / 聽歌中",
  "title": "音樂推薦",
  "description": "長期收藏那些會讓場景切換的聲音。",
  "url": "/categories/音樂/",
  "linkLabel": "PLAY THE ARCHIVE ↗"
}
```

`archived` 是保留的內部紀錄，不是目前首頁主要入口。不要把已移除的書籍清單重新放回首頁版型。

## 新增或調整內容分類

內容入口、搜尋分類按鈕和隨機文章的分類篩選，都共用：

```text
source/_data/content-categories.yml
```

每個分類至少需要這些欄位：

```yaml
- name: 新分類
  code: NEW
  icon: fa fa-pencil
  url: /categories/新分類/
  description: 一句簡短的分類說明。
```

新增分類時，也要把文章的 `categories` 改成完全相同的名稱。只改分類設定、沒有對應文章分類，通常不會造成建置錯誤，但會讓入口內容不完整；只改文章分類、沒有先加入設定，`npm run check:content` 會提醒錯誤。

`站務` 可以保留在文章 front matter，但不要把它當成訪客內容分類。

### 標籤整理

主標籤以 `source/_data/content-tags.yml` 為唯一名單，手冊不另抄一份，避免兩邊不同步。歷史別名由同檔案的 `aliases` 登記，新增文章使用 canonical 主標籤即可。建置時由 `scripts/tag-taxonomy.js` 與 `scripts/tags-normalizer.js` 共用這份註冊表；未登錄的標籤會被日常標籤檢查攔下，先修正再發布。

## 更新圖牆與圖片

### 圖片位置與路徑

圖片放在：

```text
source/images/
```

文章內使用網站路徑，例如：

```markdown
![圖片說明](/images/my-photo.webp)
```

圖牆也使用同一個 `/images/...` 路徑。Windows 本機通常不在意大小寫，但網站部署到 GitHub Pages 後可能會區分大小寫；檔名和 Markdown 路徑要完全一致。

### 圖牆更新

目前圖牆在：

```text
source/photos/index.md
```

新增圖片時，同時確認：

1. 圖片真的存在於 `source/images/`。
2. 文章中的圖片路徑正確。
3. 如果希望它出現在圖牆，`source/photos/index.md` 也要加入對應路徑。
4. 執行 `npm run check:content`。

圖牆已採用圖片延遲載入，不需要為每張圖片另外寫 JavaScript。

圖牆篩選按鈕的數字由 `scripts/photo-wall-counts.js` 在建置時依實際卡片數自動回填，不必手動同步。`npm run check:site` 會再比對產出頁面的數字與卡片數。

## 公開草稿夾的學習紀錄

`/reading/` 是公開的學習檔案入口，資料在 `source/reading-desk.yml`，與下方 Hexo 未公開草稿不同。

新增題目只需標題與連結，例如：

```powershell
npm run record -- reading --title "想整理的題目" --url "https://example.com/reference"
```

工具自動建立主題、代碼與穩定 ID，日期預設台北今日、狀態預設 `learning`、面向為 B 面。也能使用既有文章的 `/learning/…/` 或 `/work/…/` 網址；工具會先確認文章存在且包含 B 面，不會建立文章或變更文章面向。

加入既有主題時加 `--topic "主題ID"`；來源、備註和日期可選填 `--source "來源" --note "整理方向" --date "2026-10-15"`。加 `--dry-run` 可只預覽，`npm run record -- --help` 可查看其餘選項。既有紀錄的內容與排列不會因新增被重算；新增本身不發布。

`item.date` 記錄作者指定的加入／紀錄日期，可以預先填寫，不自動改成今天；`state` 記錄學習／整理階段，完成時可改為 `published`，並用 `resolved_date` 記錄完成日期。草稿夾熱力圖與日期明細依填入的 `item.date` 顯示；改成已成文後仍保留原來的歷史紀錄，`updated` 不會把它移到修訂日。

### PNG 轉 WebP

可以將 PNG 轉成 WebP，但要把「檔案」和「所有引用路徑」一起處理：

1. 先產生新的 `.webp` 檔案。
2. 搜尋舊的 `.png` 路徑被哪些文章或頁面使用。
3. 逐一改成 `.webp`。
4. 先不要刪除舊 PNG。
5. 執行 `npm run verify`，確認沒有圖片路徑錯誤。
6. 網站預覽正常後，才考慮移除舊檔案。

不要只改副檔名，也不要先刪除原圖再慢慢找引用位置。

## 使用草稿

草稿放在：

```text
source/_drafts/
```

建立方式：

```powershell
npx hexo new draft "文章標題"
```

預覽草稿：

```powershell
npx hexo server --drafts --port 4003
```

瀏覽 `http://localhost:4003/`。確認文章完成後，再把檔案移到 `source/_posts/`，補好日期、分類和標籤。

已經公開的文章不要反覆改檔名；如果草稿要使用分類子資料夾，搬移前要確認網址是否會因此改變。

## 文章發表熱力圖與最近發表文章

文章發表熱力圖是由文章的發表 `date` 自動產生；`date` 依作者指定的發表／紀錄日期歸檔，也可以預先填寫，不依檔案 mtime 或驗證當天改寫：

- 新增文章並設定日期後，建置會更新熱力圖。
- `scripts/calendar-generator.js` 會在建置時產生 `public/calendar.json` 與 `public/calendar-posts.json`。
- `public/calendar.json` 和 `public/calendar-posts.json` 更不要手動改。
- 熱力圖下方會顯示最近一週按發表 `date` 排出的文章；點選日期格後，下方會換成該日發表的文章。介面使用「發表」語意，不把 `updated` 修訂日期當成熱力圖事件。`today` 只用來判定未來日期的顯示狀態，不會改變事件日期。

如果熱力圖數字不對，先檢查文章 front matter 的發表 `date`，再重新執行 `npm run verify`；不要用 `updated` 代替 `date`，也不要直接修改產物。

## 搜尋、導覽與版型

「全部文章」與其日期／分頁清單會直接顯示既有摘要：一般文章使用 `description` 的文字，沒有有效文字時使用 `<!-- more -->` 之前的內容；兩者都沒有就保留標題列。歌曲沿用 more 之前的歌曲資訊、插圖與收聽連結，不需要另外寫一份感想摘要或新增必填欄位。修改原稿後由建置同步，不另外維護清單副本。

日常新增文章不需要改版型。以下檔案只有在確定要調整網站結構或外觀時才修改：

- 導覽列位置：`themes/next/_config.yml`
- 導覽文字：`themes/next/languages/zh-TW.yml`
- 搜尋視窗：`themes/next/layout/_partials/search/index.njk`
- 搜尋近期清單：`scripts/search-recent-posts.js`（全部及每個分類最新十篇的聯集；完整搜尋按需載入 `search.xml`）
- 首頁：`themes/next/layout/index.njk`
- 首頁樣式：`themes/next/source/css/_custom/home.styl`（由 `main.styl` 最後載入）
- 生活索引頁：`source/reading-log/index.md`
- 碎碎念頁：`source/status/index.md`
- 更新日曆頁：`source/calendar/index.md`

分類入口、搜尋按鈕和隨機文章的篩選會讀取 `content-categories.yml`。不要為了新增一個分類，分別去改三個頁面，否則之後很容易不一致。

文章內的站內連結優先使用 `/learning/文章網址/` 這類從網站根目錄開始的路徑。摘要會出現在首頁與分頁，`../文章網址/` 會因所在頁面不同而指向錯誤位置。

## 文章底部推薦

文章頁底部的推薦由 `themes/next/layout/_macro/post.njk` 呼叫 `popular_posts_fixed({}, post)`，由 `scripts/popular-posts-fixed.js` 依文章資料自行選出已發表文章。`_config.yml` 的 `popular_posts.enable` 控制是否顯示，`popular_posts.limit` 控制最多篇數，兩者都已接到這條呼叫路徑。

可在文章 front matter 使用 `related_posts` 指定站內相對路徑；有效且已發表的指定文章會優先出現。`recommendation_topics` 是可選的推薦主題欄位，會先用主題相符度，再以 tags、categories 補足，排序採可重現的穩定順序。沒有這些欄位時仍依現有文章 tags/categories 配對。不要新增未接線的 `about`、`sameAs` 或其他關聯欄位；若日後更改 helper 設定或欄位，須同步更新實作、手冊、測試並核對產出頁面。

## 建置、預覽與發布

### 建議流程

這裡是持續更新的紀錄區：公開文章寫到哪裡就一起發布，未完成的內容日後再改。不必挑選單篇或建立另一份發布目錄；既有草稿與隱私設定仍生效。

只想本機預覽時執行：

```powershell
npm run server
```

準備上線直接使用下方的「發布」指令即可，不必先手動跑一輪 verify。需要單獨檢查而暫不上線時才執行 `npm run verify`。

`npm run verify` 自動選擇檢查範圍。有成功完整基準時，依以下分類處理；首次使用或驗證工具升級後仍需先完成一次全套檢查。

| 這次修改 | 系統會做什麼 |
| --- | --- |
| `source/_posts/` 的文章 Markdown、`source/images/` 的 PNG／JPEG／GIF／WebP／AVIF／ICO 圖片、`source/microblog.json`、`source/life-index.json`、`source/reading-desk.yml` | 內容更新檢查、重新建置網站及檢查產物；略過整套程式回歸測試，保留碎碎念歷史保護與紀錄資料同步檢查 |
| 根目錄或 `docs/` 裡的一般 Markdown 說明、進度或歷史紀錄 | 不因這些文件的變動重新建置；已有同日有效候選時直接沿用 |
| 程式、版型、設定、檢查器、其他資料、SVG 圖片，以及檢查器使用的 `docs/dual-surface-visual-rules.md` | 完整驗證 |

相同來源與產物的成功結果可在同一台北日期內沿用，不重跑建置與測試。需要刻意重跑全套才使用 `npm run verify:full`。新網站會先建置，再讓程式測試讀取索引，避免使用舊產物。

內容更新仍需建置整站並檢查連結／生成資料，並非每次只需幾秒。`life-index.json` 與 `reading-desk.yml` 會逐欄位核對來源與輸出，包含陣列順序。一般舊碎碎念已可正常修改與排序；既有 ID 與隱私清理保護仍保留，詳見「更新碎碎念」。

`npm run check:site` 可單獨檢查已建置的網站。同網域的獨立專案需在 `tools/site-check.config.json` 記錄路徑與理由，例如 `/lifecheck/`；這些專案不由本網誌產生，需另外確認線上是否可用。檢查不會自動驗證所有外部網站的可用性。

需要驗收前端異常處理時，可在建置後使用本機故障預覽（只改 HTTP 回應，不會改寫 `public/` 或發布網站）：

```powershell
node tools/preview-faults.js animation 4004
node tools/preview-faults.js search-once 4005
```

兩個指令要各開一個終端機執行，分別開啟 `http://127.0.0.1:4004/` 與 `http://127.0.0.1:4005/`。前者模擬動畫檔 404，文章仍應可讀；後者第一次讀取搜尋索引會失敗，按「重新載入」後應能搜尋。測試後按 `Ctrl + C` 停止。正式頁面不會啟用這些故障。

預覽請開啟終端機顯示的網址，預設為 `http://localhost:4000/`。測試完畢後，在 PowerShell 按 `Ctrl + C` 停止本機伺服器。

### 發布前快速檢查

- 首頁能開啟。
- 文章分類正確。
- 搜尋可以找到新文章。
- 圖片沒有破圖。
- 有修改圖牆、熱力圖或碎碎念時，再檢查對應功能；單純改文章不必每次重做這些人工檢查。

### 發布

日常只需要一個指令：

```powershell
npm run publish -- --execute
```

它會自動檢查目前整站、提交全部原稿修改、推送 `source` 備份，最後發布整站到 `main`。原稿包含文章、圖片、資料、程式、設定與文件；已暫存及未暫存修改都以目前檔案內容保存。生成網站、暫存目錄和 Git 忽略檔案不會自動加入來源備份。一般未完成公開文章不會被阻擋；格式錯誤、隱私規則或無法備份的建置輸入仍需修正。

日常輸出只顯示流程階段與 GitHub Pages 狀態。完整執行記錄每次另存於 `node_modules/.cache/blog-publish-*.log`，不會覆寫舊記錄；失敗訊息會附上可直接開啟的完整路徑。

可以選填這次更新的說明：

```powershell
npm run publish -- --execute --message "更新最近的閱讀與生活紀錄"
```

只想看這次會處理哪些修改，執行 `npm run publish`；這是可選的預覽，不會提交、推送或部署。

驗證失敗時不提交或部署；來源推送失敗時保留本機提交；部署失敗時保留已成功的來源備份。同一版本中途失敗可接續：

```powershell
npm run publish -- --execute --resume
```

如果失敗後又改了內容，直接重新執行一般發布指令，按目前整站內容處理。Git 提交失敗或 hook 改動時，先查看錯誤、`git status` 與最近提交；工具不會自行 reset 或清掉暫存區。若程式被強制關閉留下 `node_modules/.cache/blog-publish.lock`，確認沒有其他發布程序執行後再移除該鎖檔。

`publish` 推送網站後會查詢 GitHub Pages，只有完成建置的版本與本次部署的 `main` SHA 相同，才顯示已確認完成。等待建置、建置失敗或無法查詢會分別說明；查詢失敗不會撤回已完成的來源備份與部署推送。

若顯示 Pages 尚待確認，稍後只查狀態即可，不必重新發布：

```powershell
npm run check:pages
```

狀態查詢使用已安裝並登入的 GitHub CLI（`gh`）。沒有可追溯的發布紀錄時會顯示無法確認，不憑目前網站內容推定這次修改已上線。這個指令不會建置、提交或部署。

既有 `npm run deploy` 保留供維護用途，只做驗證與網站部署，不會備份來源或建立 `publish` 的完整狀態紀錄，日常請用 `publish`。相同候選會重用驗證結果，不另外重跑全套。GitHub Pages 完成建置後才算線上更新；指令推送完成不代表已確認網站上線。

## 常見錯誤處理

### `JSON.parse` 或 JSON 格式錯誤

通常是少了逗號、引號沒有成對，或把半形引號改成全形引號。優先檢查最近新增的那一筆資料。

### 顯示未知分類

確認文章 front matter 的分類是否完全符合 `content-categories.yml` 的 `name`，不要自行縮寫。

### 圖片破圖

確認實際檔案位於 `source/images/`，再確認 Markdown 使用的是 `/images/...` 網站路徑，不是 `C:\\Users\\...` 的本機路徑。

### 熱力圖沒有反映發表日期

確認文章有正確的作者指定發表 `date`；`updated` 修訂日期不會新增熱力圖格，接著重新執行：

```powershell
npm run verify
```

不要編輯 `calendar.json` 或 `calendar-posts.json`。

### 建置成功但畫面沒有變

瀏覽器可能保留舊快取。先重新整理，或用無痕視窗查看；也確認你修改的是 `source/` 原始檔，而不是 `public/` 產物。

## 不要做的事

- 不要手動修改 `public/`。
- 不要手動修改熱力圖產物。
- 不要為了新增文章去改首頁 CSS。
- 不要任意改已發布文章的檔名、路徑或圖片檔名。
- 不要把 Windows 本機完整路徑貼到文章裡。
- 不要用 `git reset --hard` 清理問題。
- 不要為了「整理」而刪除舊的碎碎念或圖片；先確認是否仍被文章引用。

## 最短版流程

```text
新增或修改 source 裡的原始資料
        ↓
npm run publish -- --execute
```

發布工具會依本次修改自動驗證、提交原始資料、推送 source 備份並部署整站。需要看畫面時，可先用 `npm run server` 預覽；這是選用步驟。只想檢查而暫不上線時才單獨執行 `npm run verify`。最後簡短交代原始資料備份與網站發布各自的狀態即可，不另建逐篇驗收文件。
