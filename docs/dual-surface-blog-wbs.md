# 雙面部落格施工 WBS

狀態：2026-09-28 WBS 0.1～10.7 已完成；作者已核准本次發布，WBS 11.1～11.3 部署、線上冒煙測試與發布紀錄完成  
上位設計：[雙面部落格詳細計畫](dual-surface-blog-plan.md)  
適用專案：`C:\Blog\blog-1988`

## 1. 施工目標

在保留文章網址、內容、B 面隨機用途及未提交修改的前提下，建立同一個公開網站的兩個固定入口：

- A 面 `/`：工作與學習，供履歷讀者快速理解作者的問題拆解、學習與工作方式；`/profile/` 保留相容入口。
- B 面 `/memory/`：個人記憶庫，維持作者優先的隨機重逢與自由探索。
- 一篇文章只保留一份來源、一個公開網址與一個 canonical，但可以被 A、B 兩個入口共同引用。
- A／B 是公開內容的呈現範圍，不是隱私權限；私人內容完全不進公開建置。

## 2. 不可變更的施工原則

以下是本 WBS 的固定前提。若未來要推翻其中任何一項，必須先停止施工、修改上位設計並重新取得使用者確認。

1. `/` 是 A 面預設入口，`/memory/` 是 B 面固定入口；`/profile/` 保留為 A 面相容入口。此項依作者 2026-09-28 最新決定覆寫早期路由決議。
2. 不建立 A 版、B 版兩份相同文章。
3. `surfaces: [profile, memory]` 代表同一篇文章能在兩面被找到。
4. 舊文章缺少 `surfaces` 時預設為 `memory`；新文章上線前必須明確選擇。
5. A 面首頁採最新活動年份的文章活動熱力圖，完整 A 面內容放 `/profile/articles/`；早期三路徑／代表卡方案已退役，僅保留內部資料供相容與回歸驗證。
6. B 面保留隨機文章作為主要互動，不改成最新文章流水首頁。
7. 探索中內容可以公開，但必須標示成熟度、最近校準日期與適用邊界。
8. 切換依靠真實網址及普通連結；JavaScript 只增強動畫，不決定目前面向。
9. B 面不稱私人模式；真正私人內容不得進入 `source/` 的公開資料來源或 `public/`。
10. 不變更既有文章 permalink、日期、正文及既有 microblog ID。
11. 一次只執行一個可保存、可驗證的小步驟；未驗證不標完成。
12. 部署是獨立工作包，只有使用者針對當次部署明確授權後才能執行。
13. 不使用任何額度重置券，除非使用者針對該次重置另行明確授權。

## 3. 範圍

### 本次計畫包含

- `surfaces` 與思考成熟度的內容資料契約。
- 公開／私人來源邊界與建置洩漏檢查。
- A 面首頁、A 面完整清單與 A／B 切換。
- 文章在兩面共同引用時的唯一網址、標記與返回入口。
- 搜尋、最近文章、內容清單與隨機抽籤的面向規則。
- 發布範本、驗證器、作者操作說明及維護規則。
- 桌面、手機、無 JavaScript、鍵盤、減少動態、SEO 與公開輸出驗收。

### 本次計畫不包含

- 會員登入、密碼保護或真正的私人閱讀區。
- 第二個網域、第二套 Hexo 專案或文章內容同步系統。
- 為所有舊文章重寫正文或一次補齊成熟度。
- 自動用 AI 判斷文章是否適合履歷。
- 為追求流量而加入推薦演算法、熱門排行或廣告追蹤。
- 未經確認的部署、履歷外部連結修改或第三方平台發布。

## 4. 角色與決策權

實際施工時可能由同一個人或代理程式兼任多個角色，但每次驗收必須分別站在這些角色的標準檢查，不能只用工程可運作作為完成依據。

| 角色 | 主要關心 | 決策權／責任 |
|---|---|---|
| 作者／產品負責人 | 網站是否仍像自己、哪些內容能公開、A 面內容範圍是否合適 | 內容邊界、A 面首頁、文案與部署的最終核准者 |
| 履歷讀者／招募者 | 能否在 30～60 秒理解能力與思考方式 | 驗收 A 面掃讀性，不決定作者私人內容 |
| 內容編輯 | 發布流程是否簡單、欄位是否容易長期維護 | 定義編輯檢查表、成熟度與策展流程 |
| 資訊架構師 | 一篇文章是否只有一個身份、入口是否清楚 | 負責 surface、路由、搜尋與去重規則 |
| 隱私／公開邊界審查者 | 是否有資料因「畫面沒顯示」而被誤認為私人 | 對公開建置洩漏具有停止施工權 |
| UX／無障礙設計者 | 切換能否理解、鍵盤與無腳本是否可用 | 驗收互動、文字標籤、手機與減少動態模式 |
| SEO／內容技術審查者 | canonical、sitemap、搜尋結果是否因雙面而重複 | 驗收單一文章網址及索引一致性 |
| Hexo 實作工程師 | 共用規則、建置穩定性、測試與維護成本 | 實作程式、測試、文件與回復方案 |
| QA 驗收者 | 規劃行為與實際產物是否一致 | 以真實頁面、輸出檔及瀏覽器驗證，不接受未驗證完成 |

### 簡化 RACI

| 決策／工作 | 作者 | 內容編輯 | 架構／工程 | 隱私 | UX／SEO／QA |
|---|---|---|---|---|---|
| 公開邊界 | A | C | I | R | I |
| `surfaces` 規則 | A | C | R | C | C |
| 首批文章歸類 | A/R | C | I | C | I |
| A 面內容範圍與首頁呈現 | A/R | C | I | I | C |
| 程式與測試 | I | C | A/R | C | C |
| 視覺與互動 | A | C | R | I | R |
| 部署 | A | I | R | C | C |

`A` = 最終負責；`R` = 執行；`C` = 必須諮詢；`I` = 告知結果。

## 5. 模擬跨角色設計審查

以下是同一方案分別由不同角色提出意見的模擬討論，不是假裝有外部真人參與；用途是讓施工前的衝突與取捨可見。

### 議題一：根首頁應該給誰看

**履歷讀者：** 如果打開網站先看到隨機歌曲或生活內容，我不一定知道作者希望我看什麼。專業入口必須直接而穩定。

**作者：** 但這個網站首先是自己的記憶庫，不能因為偶爾放入履歷，就永久把根首頁改成作品集。

**資訊架構師：** 不必二選一。履歷使用固定 `/profile/`；根首頁 `/` 保留作者使用方式。兩個網址都不依賴上次切換狀態。

**歷史決議：** 原方案以 `/profile/` 作履歷入口、`/` 保留 B 面。2026-09-28 作者在本機預覽後改為 `/` 預設顯示 A 面、`/memory/` 固定顯示 B 面；`/profile/` 僅保留相容。這仍不是 A/B 測試，而是由網址決定的穩定入口。

### 議題二：翻面要多隱密

**作者：** 希望有一點發現秘密空間的樂趣。

**UX 設計者：** 可以低調，但不能只放沒有名稱的圖示。否則鍵盤使用者、螢幕閱讀器與第一次造訪的人不知道會去哪裡。

**履歷讀者：** A 面首屏不應被大型遊戲化機關搶走注意力。

**決議：** 使用清楚的文字 `SIDE B／翻到個人記憶庫` 與 `SIDE A／看工作與學習`；A 面按鍵低調但可辨識，B 面保留較強的翻面趣味。動畫不是完成條件，普通連結才是。

### 議題三：同一篇工作文章要不要複製

**內容編輯：** 複製後每次改錯字、更新結論都要改兩篇，很快就不同步。

**SEO 審查者：** 兩個正文網址也會增加 canonical、sitemap 與搜尋去重的負擔。

**作者：** 但工作文章確實同時是履歷證據和個人記憶。

**資訊架構師：** 保留單一文章，在 A 面與 B 面各建立入口卡；文章以 `surfaces: [profile, memory]` 表示雙面資格。

**決議：** 一份正文、一個 URL、兩個入口；搜尋「全部公開內容」仍只出現一筆。

### 議題四：A 面是否自動收所有工作分類

**Hexo 工程師：** 從分類或檔名自動判斷最省初期標記工作。

**履歷讀者：** 分類為工作不等於適合第一印象；流水帳和成熟方法文章不應同權重。

**內容編輯：** 自動判斷也會讓作者不清楚為什麼文章突然出現在履歷頁。

**決議（現行）：** `profile` 必須明確標記，不從分類、標籤或檔名推測。A 面首頁以全部已發布 profile 文章的 `date`／合法 `updated` 活動事件產生最新年份熱力圖，完整清單呈現全部合格文章。早期人工策展 6～10 篇及三路徑方案已被熱力圖取代；`profile-home.yml` 不再決定公開首頁內容。

### 議題五：未完成內容能不能上 A 面

**履歷讀者：** 未完成如果沒有說明，容易被誤認為作者的正式結論。

**作者：** 學習過程與自我校準正是網站的重要部分，不想只留下成功後的答案。

**內容編輯：** 將「展示面向」與「成熟度」分開即可。探索中不代表不專業，沒有標示才是問題。

**決議：** 探索中內容可以進 A 面，但必須有 `thinking_status`、最近校準日期及適用邊界。狀態在文章頁呈現；A 面目前沒有代表卡，熱力圖只顯示文章活動與原文連結。

### 議題六：B 面是否等於安全的私人角落

**隱私審查者：** 只要能從網址打開、存在 JSON 或進入 `public/`，就是公開資料。按鍵低調、選單不顯示或搜尋不收錄都不構成隱私。

**作者：** B 面仍想保留較真實的生活和工作感受。

**內容編輯：** 可以公開的是經過咀嚼、去除他人隱私和專案細節後的版本；原始情緒和內部資料留本機私人來源。

**決議：** B 面稱「個人記憶庫」而非私人模式。私人文章、碎碎念與學習資料不進公開來源；不以 `surfaces`、CSS 或前端過濾代替權限。

### 議題七：搜尋要不要完全分成兩套

**履歷讀者：** A 面搜尋預設不應先出現大量歌曲和生活紀錄。

**作者：** 自己有時會記得文章內容，卻不記得它當初被分在哪一面。

**工程師：** 兩套索引會造成更新與去重風險。

**決議：** 只產生一份統一索引，每筆帶 `surfaces`。A 面預設篩 `profile`、B 面預設篩 `memory`、直接從文章開啟預設「全部公開內容」，而且使用者隨時能切換範圍。

### 議題八：兩面要不要像兩個完全不同的網站

**視覺設計者：** A 面可以較像工作台，B 面延續磁帶、收藏與記憶語彙。

**作者：** 希望有翻面的驚喜。

**UX 設計者：** 若字體、品牌、位置和操作全變，訪客會以為離開原站，也增加手機與無障礙維護成本。

**決議：** 共用品牌、排版骨架、文章版型和操作邏輯；只調整強調色、首頁內容密度與裝飾語彙。先完成資訊架構，再做翻面動畫。

### 角色審查後的共同結論

```text
不是兩個網站
    ↓
是一個作者的兩個公開入口
    ↓
A 面負責快速理解，B 面負責長期探索
    ↓
文章、搜尋資料與網址維持單一來源
    ↓
私人內容位於整個公開系統之外
```

## 6. WBS 使用方式

- WBS 編號是後續施工、進度紀錄與驗收的共同識別。
- 每次工作開始前，先確認上一個相依工作包已完成並有驗證紀錄。
- 每次原則上只選一個工作包；若工作包在實作時仍過大，先拆成 `.a`、`.b` 子步驟，不跨過驗收點。
- 每個工作包完成時都要記錄：修改內容、實際驗證、未完成事項、下一個工作包、是否部署。
- 工作量是相對複雜度，不是承諾日期：`S` 小、`M` 中、`L` 大；`L` 一律在施工前再拆小。
- `HOLD` 表示必須取得作者決定後才能繼續；技術完成不能代替內容或部署核准。

## 10. 每個工作包的完成定義

工作包只有符合全部條件才標為完成：

1. 產出已保存到專案或約定位置。
2. 沒有覆蓋進場前未提交修改。
3. 已執行與風險相稱的目標測試。
4. `git diff --check` 通過；若是程式工作，相關回歸測試也通過。
5. 實際驗證結果已寫入 `docs/personal-navigation-progress.md`。
6. 已記錄下一個 WBS ID，沒有把未做事項包裝成完成。
7. 未經授權沒有部署。

## 11. 施工時的停止條件

遇到以下任一情況，該輪停止擴大修改並先回報：

- 無法確認內容是否能公開或是否涉及他人／專案資料。
- 候選文章需要大幅改寫才適合 A 面。
- 必須更改既有 permalink、文章日期或 microblog ID 才能繼續。
- A／B 規則在不同產生器產生不一致結果。
- 需要把同一篇正文產生成兩個 URL。
- 完整建置、目標測試或公開輸出稽核失敗。
- 實作需要登入、伺服器權限或其他超出本 WBS 的新能力。
- 即將部署但沒有當次明確授權。

## 14. 參考設計原則

- [Andrew Braun](https://www.andrewbraun.dev/)：同一個人以 Professional／Personal／Nerd 模式呈現不同閱讀角度。
- [Tom Critchlow](https://tomcritchlow.com/new-homepage2/)：用同一網站的顧問、Blog、Wiki 與個人領域提供不同入口。
- [Maggie Appleton：Digital Garden](https://maggieappleton.com/garden-history)：以內容成熟度、建立與最近整理日期說明公開但未完成的思考。
- [Diego's Digital Garden](https://garden.diego.codes/)：公開花園只是全部私人筆記的可公開子集。
- [Hexo front matter](https://hexo.io/docs/front-matter)：文章資料與 permalink 留在單一來源，由 metadata 支援不同分類及呈現。
- [Google canonical 說明](https://developers.google.com/search/docs/crawling-indexing/canonicalization)：避免相同正文分散到多個 URL，維持單一代表頁面。

這些案例用來驗證架構方向，不要求網站模仿它們的外觀或個人品牌。
