## 1. 核心決策

網站不是拆成兩個部落格，而是同一座公開記憶庫的兩個觀看入口：

| 面向 | 正式名稱 | 主要對象 | 首頁任務 | 固定入口 |
|---|---|---|---|---|
| A 面 | 工作與學習 | 履歷讀者、未來同事、第一次認識作者的人 | 快速理解作者如何拆題、學習與工作 | `/`（`/profile/` 相容） |
| B 面 | 個人記憶庫 | 作者自己、朋友、想繼續探索的人 | 隨機重逢歌曲、作品、生活與思考 | `/memory/` |

根首頁 `/` 直接呈現 A 面，履歷與一般訪客不需先知道子路徑；`/profile/` 仍可作既有 A 面連結的相容入口。作者的隨機探索 B 面固定於 `/memory/`。兩個入口都有一個清楚但帶點趣味的「翻到另一面」按鍵。

這個設計帶來三個好處：

1. 不必犧牲作者自己最常用的隨機探索首頁。
2. 履歷讀者不用先穿過歌曲、日記與碎碎念，便能理解專業脈絡。
3. 願意多探索的人仍可翻到 B 面，看見工作能力之外的完整個性。

「秘密感」來自發現另一面，不來自技術上的隱藏。B 面仍是公開網站，搜尋引擎、知道網址的人與站內全站搜尋都可能找到其中內容。

## 2. A／B 與公開／私人是兩條不同的軸

這是整個方案最重要的邊界：

```text
                 公開內容
                    │
          ┌─────────┴─────────┐
          │                   │
      A 面呈現             B 面呈現
   工作／學習脈絡          個人記憶探索
          │                   │
          └────同一篇文章─────┘

私人內容：不進入公開建置，因此不屬於 A 面或 B 面
```

- `A`、`B` 只決定一篇公開內容會在哪個入口被推薦、搜尋或抽到。
- 它們不是權限，也不是保密機制。
- 真正不能公開的內容，不能只靠 CSS 隱藏、按鍵切換或索引過濾；它必須根本不進入 `public/`。

### 私人內容的實際處理

| 內容形式 | 可公開版本 | 私人版本 |
|---|---|---|
| 一般文章 | `source/_posts/` | `source/_drafts/`，並維持草稿不建置；更敏感者放在專案外的私人資料夾 |
| 碎碎念 | `source/microblog.json` 只保留可公開項目 | 另存本機私人檔，且不放在 `source/`、不加入 Git |
| 學習資料 | `source/reading-desk.yml` 只保留可公開項目 | 原始私人筆記放在公開建置來源之外 |
| 他人資料／未公開專案 | 去識別、抽象成方法後才公開 | 原文只留私人位置 |

特別注意：`source/microblog.json` 與 `source/reading-desk.yml` 位於公開來源目錄。即使畫面不顯示，來源檔或建置產物仍可能被讀取，所以不能把私人內容放進去，再期待 A／B 篩選替它保密。

## 3. 一篇文章如何同時放在 A、B

### 3.1 只保留一篇正文與一個網址

文章 front matter 增加 `surfaces`，只描述它適合在哪些公開面向出現：

```yaml
---
title: 網站品質與軟體測試
surfaces:
  - profile
  - memory
---
```

允許值只有：

- `profile`：A 面，工作與學習。
- `memory`：B 面，個人記憶庫。

四種情況的行為如下：

| front matter | A 面 | B 面 | 原文章網址 |
|---|---:|---:|---|
| `surfaces: [profile]` | 顯示 | 不主動呈現 | 保持可開啟 |
| `surfaces: [memory]` | 不顯示 | 顯示 | 保持可開啟 |
| `surfaces: [profile, memory]` | 顯示 | 顯示 | 只有同一個網址 |
| 沒有 `surfaces` | 不顯示 | 顯示 | 保持現況 |

舊文章缺少欄位時預設為 `memory`，原因是不能因為推出履歷入口，就把 265 篇既有文章突然全部放進專業面。A 面必須由作者明確挑選；B 面則完整承接現有網站。

### 3.2 為什麼不複製文章

同一篇文章標為 `[profile, memory]` 後：

- A 面卡片連到原文章網址。
- B 面抽籤也連到同一網址。
- `navigation-index.json` 只有一筆文章紀錄，紀錄內是 `surfaces: ["profile", "memory"]`。
- canonical、留言、更新、搜尋結果與瀏覽紀錄都不會分裂。
- 修改正文只改一個檔案，不會出現 A 版與 B 版內容不同步。

也就是說，「同時放 A、B」是同一篇內容被兩種入口引用，不是產生兩份文章。

### 3.3 額外欄位只處理 A 面策展（歷史方案）

`surfaces` 只決定有沒有資格出現在某一面，不負責首頁排序。早期 A 面三條代表路徑另由 `source/_data/profile-home.yml` 管理；該公開 UI 已由熱力圖取代，資料目前只保留作內部相容與回歸驗證。以下是當時的概念示例；`workingDescription` 從未輸出到公開頁面：

```yaml
paths:
  - id: observe-context-and-needs
    title: 看見現場與需求
    workingDescription: 內部策展備註，不顯示於公開頁面。
    workingDescriptionVisibility: internal
    items:
      - url: /work/from-real-work-to-features/
        role: featured
        status: published-note
```

這樣可以把「文章屬於哪一面」和「A 面首頁現在要主推什麼」分開：

- 文章 front matter 是長期內容屬性。
- `profile-home.yml` 是可隨履歷目標調整的策展清單。
- 調整首頁順序不會改文章網址，也不必改文章本身。
- 驗證程式必須攔下不存在的網址、重複引用，以及沒有 `profile` 資格卻被放上 A 面的文章。

## 4. 內容判斷標準與範例

### A 面：工作與學習

一篇內容只要能讓陌生人看懂「問題、判斷、做法、學到什麼」，就可以進 A 面；不要求寫成成功案例，也不必把迷惘修飾掉。

適合 `[profile, memory]` 的例子：

- 「從實際抽象功能」系列：既是工作能力證據，也是個人成長軌跡。
- 「網站品質與軟體測試」學習路徑：呈現系統化學習，也值得日後自己回看。
- API 需求排查、上稿與表格排查：去除客戶、公司與未公開專案細節後，保留可遷移的方法。
- AI 提問判斷順序：能看見思考框架，不只是工具心得。
- N+days 中已經整理出工作觀察、方法與反思的篇章。

可能只放 `[profile]` 的內容：

- 專門寫給履歷讀者的「如何閱讀這個網站」或能力索引頁。
- 高度導覽性、離開 A 面就沒有獨立記憶價值的說明頁。

### B 面：個人記憶庫

適合 `[memory]` 的例子：

- 歌曲推薦、閱讀與觀影紀錄。
- 旅行、生活片段、身體感受與日常觀察。
- 不適合作為履歷第一印象，但三年後仍希望自己找得回來的文章。
- 經過整理、可以公開的碎碎念與探索中筆記。

### 完全不公開

- 純負面宣洩，還沒有整理出自己真正想說什麼。
- 可辨識的同事、主管、客戶或親友衝突。
- 未公開的專案名稱、內部流程、帳號、數字、文件或商業資訊。
- 別人的故事與隱私，即使作者本人不介意公開。
- 仍需要依賴「應該沒人會按到那顆按鍵」才敢放上站的內容。

判斷捷徑：如果一篇內容不能被任何公開網址直接開啟，就不應進 A／B 系統；如果可以公開、只是第一印象不適合履歷，就放 B，而不是假裝把它藏起來。

## 5. 兩個首頁的資訊架構

### 5.1 A 面 `/profile/`

> 歷史設計備註：本節的三路徑、代表卡與最近學習描述是早期 WBS 5.x 方案；現行封面已由最新活動年份熱力圖取代，完整內容另放 A-only 可篩選文章庫。現行規格見 [10.6 作者驗收包](dual-surface-blog-10.6-author-acceptance.md) 與 [文案契約](dual-surface-copy-contract.md)。

A 面採極簡呈現，靠分類標題與文章卡片說話；不顯示定位段落、tagline、intro 或路徑補充說明。頁面標題為「經驗與方法」，三條路徑依序為「看見現場與需求」、「整理資訊與方法」、「實作、驗證與修正」。`profile-home.yml` 的 `workingDescription` 僅為內部策展備註，不供版型顯示。

版面資料只提供以下標籤與內容：

- 頁面標題：`經驗與方法`
- 最近學習區標題：`最近正在學`
- 完整清單入口：`看全部`
- 翻面連結：`SIDE B／翻到個人記憶庫`
- 三條路徑的文章卡片直接使用既有單一文章 URL，不另寫路徑介紹段落。

A 面不複製完整履歷、不放公司機密，也不加入公開補充說明或定位文案。

### 5.2 B 面 `/`

B 面延續現有首頁的作者優先邏輯：

1. 保留 Welcome Board 與「1995 後的我的想法」主題。
2. 隨機文章卡仍是主角，只從含 `memory` 的文章中抽取。
3. 保留歌曲／閱讀抽籤、生活索引、草稿夾、記憶圖牆與更新日曆。
4. 增加「翻到 A 面：工作與學習」按鍵。
5. 含 `[profile, memory]` 的工作文章仍可能在這裡被抽到，因為工作經驗也是個人記憶的一部分。

### 5.3 切換按鍵

按鍵應該有趣，但不能讓第一次使用的人猜：

- A 面顯示：`SIDE B ／ 翻到個人記憶庫`。
- B 面顯示：`SIDE A ／ 看工作與學習`。
- 技術上使用普通 `<a>` 連結，而不是只靠 JavaScript，停用腳本時仍能切換。
- `/profile/` 與 `/` 是網址真相；重新整理、分享連結與開新分頁不會跑到另一面。
- 動畫只做短暫的翻面感，並尊重 `prefers-reduced-motion`。

## 6. 導覽、搜尋、抽籤與文章頁規則

### 6.1 主選單

A 面選單聚焦：

- A 面首頁
- 代表路徑
- 全部工作與學習
- 搜尋
- 翻到 B 面

B 面沿用目前選單：

- 首頁
- 全部文章
- 內容分類
- 生活索引
- 草稿夾
- 記憶圖牆
- 更新日曆
- 翻到 A 面

不要直接改成一份全站共用的大選單，否則 A 面仍會被所有個人入口淹沒。版型依目前頁面的固定入口決定選單，不使用可失效的前端記憶猜測模式。

### 6.2 搜尋

`navigation-index.json` 每筆公開紀錄增加 `surfaces`，搜尋只過濾索引，不建立第二份索引：

- 在 A 面開啟搜尋：預設勾選「工作與學習」。
- 在 B 面開啟搜尋：預設勾選「個人記憶庫」。
- 搜尋介面提供「全部公開內容」，讓使用者主動跨面查找。
- `[profile, memory]` 的文章在「全部公開內容」仍只出現一次。
- 直接從一般文章頁開啟搜尋時，預設「全部公開內容」，避免系統猜錯來處。

目前學習題目會合併進文章搜尋紀錄，因此需增加一條資料規則：連結到文章的學習題目，其 `surfaces` 必須是該文章 `surfaces` 的子集合；不能靠學習題目把原本只屬於 B 面的文章意外帶進 A 面。獨立學習題目則使用自己的 `surfaces`。

### 6.3 隨機抽籤

- 首頁與 `/random/` 只讀取含 `memory` 的文章。
- 站務文章、私人內容與只屬於 `profile` 的導覽頁不進抽籤。
- `[profile, memory]` 仍可被抽到。
- 現有分類平衡、換一篇與返回恢復機制繼續保留。
- 若未來想做「隨機看一篇工作方法」，應另加 A 面按鈕，不改 B 面抽籤的用途。

### 6.4 文章頁

- 一般文章頁維持中性，不複製成 A 版、B 版。
- 顯示一個小型面向標記，例如 `工作與學習・個人記憶`，但不喧賓奪主。
- 從哪一面進入，就讓瀏覽器上一頁自然回到那一面，不用改寫文章網址。
- 文章內的分類、標籤與相關文章仍是全站關係；第一版不把它們硬切成兩套。
- 搜尋引擎只看到原文章 canonical，不會產生重複內容問題。

## 7. 未完成筆記的整合方式

探索中的文章可以公開，但 A 面不能讓讀者把假設誤認為結論。建議統一使用：

```yaml
thinking_status: exploring
thinking_updated: 2026-09-25
thinking_boundary: 目前只整理個人實作經驗，尚未涵蓋大型團隊情境。
```

頁首資訊塊顯示：

- `🚧 當前假設／探索中`
- `📅 最近校準`
- `📌 目前適用邊界`

這些欄位描述文章成熟度，不決定 A／B。只要思考夠精準，探索中的學習文章仍可標成 `[profile, memory]`。

## 8. 資料與程式改動藍圖

下列保留 2026-09-25 的預計影響範圍作施工歷史；實際完成狀態與後續替代方案以 WBS／驗收包為準：

| 區域 | 預計工作 |
|---|---|
| 共用規則 | 新增一個 surface 正規化工具，處理允許值、去重與舊文章預設值 |
| 文章資料 | 為首批 A 面文章加入 `surfaces`；其餘舊文章自動視為 `memory` |
| A 面策展（歷史） | `source/_data/profile-home.yml` 曾管理三條路徑與代表文章；公開呈現已退役，資料只供內部驗證 |
| A 面頁面（現行） | `/profile/` 使用最新活動年份熱力圖，`/profile/articles/` 提供完整可篩選文章庫；不動既有文章網址 |
| 隨機資料 | `scripts/random-generator.js` 只輸出含 `memory` 的合格文章 |
| 統一搜尋 | `tools/lib/navigation-index.js` 輸出 `surfaces`；搜尋介面增加目前面向／全部公開內容篩選 |
| 內容清單 | `scripts/content-browser.js` 支援依 `profile` 產生 A 面文章清單；原「全部文章」維持完整公開集合 |
| 最近文章 | `scripts/search-recent-posts.js` 可依入口提供合適的最近內容 |
| 主選單 | header 選單版型依 `/profile/` 與 `/` 選擇 A／B 導覽，保留無腳本連結 |
| 文章標記 | 文章頁顯示所屬面向，不另建文章副本 |
| 公開邊界 | 檢查公開資料檔沒有私人旗標或未允許內容；私人資料移出 `source/` 並排除 Git |
| 回歸測試 | 擴充 random、navigation index、search recent、首頁與 site check 測試 |

共用 surface 工具很重要：不能讓隨機、搜尋、首頁和清單各自解讀一次欄位，否則之後很容易發生 A 面看得到、搜尋卻找不到的分歧。

## 9. 分階段執行計畫

每一階段都遵守「完成、驗證、記錄後才進下一步」。不把整套功能一次塞進同一輪。

### 第 0 步：凍結決策與內容樣本（本文件）

產出：確認 A／B 定義、網址、缺省規則、公開邊界與驗收矩陣。  
驗收：文件能明確回答一篇文章如何只在 A、只在 B、同時在兩邊，以及私人內容如何處理。  
停止點：不改網站畫面。

### 第 1 步：建立 surface 資料契約與驗證器

產出：共用 `surfaces` 正規化工具、無效值檢查、舊文章預設 `memory`，以及對應單元測試。  
驗收：`profile`、`memory`、雙面、缺欄位、重複值與錯字都有固定結果；網站外觀不變。  
停止點：只建立資料規則，不建立 A 面。

### 第 2 步：公開邊界盤點

產出：逐項檢查公開文章、碎碎念與草稿夾資料來源；把不應建置的資料移到本機私人位置，建立不含內容本身的檢查規則。  
驗收：私人樣本不出現在 `public/`、搜尋索引、`random.json`、sitemap 或可直接請求的資料檔；公開項目的既有 `id` 不變。  
停止點：不改公開內容的文意，也不憑代理判斷刪除作者資料；邊界不確定者列待確認清單。

### 第 3 步：首批文章分類

產出：先選 10～15 篇有代表性的工作／學習文章標成 `[profile, memory]`；特殊 A 面說明頁才使用 `[profile]`。  
建議首批來源：

- 「從實際抽象功能」系列。
- 「網站品質與軟體測試」及其相關測試、發布品質筆記。
- AI 提問判斷順序。
- API、上稿與表格排查中已完成去脈絡化的工作知識。

驗收：只改 front matter，不改正文、日期與 permalink；未分類舊文章仍完全照常出現在 B 面。  
停止點：先交付內容對照表給作者檢查，不自動用分類或關鍵字把整批文章推進 A 面。

### 第 4 步：建立 A 面靜態首頁（歷史方案，完成後已被取代）

歷史產出：`/profile/`、三條代表路徑、近期學習內容與全部工作／學習入口；當時先不做翻面動畫。  
歷史驗收：停用 JavaScript 仍可閱讀和開啟文章；每個代表連結存在且有 `profile` 資格；沒有 B 面專屬內容混入。  
現況：此方案已由活動熱力圖與 `/profile/articles/` 取代；保留本段只為追溯施工順序。

### 第 5 步：加入雙面切換與情境選單

產出：A、B 兩面互相切換，並各自顯示合適選單；網址決定目前面向。  
驗收：直接開啟、重新整理、新分頁、瀏覽器上一頁、PJAX 與停用 JavaScript 都不會切錯；鍵盤與螢幕閱讀器可辨識按鍵目的。  
停止點：動畫尚可不做，先確認資訊架構。

### 第 6 步：讓搜尋、清單與抽籤理解面向

產出：索引帶 `surfaces`；A／B 搜尋預設範圍不同但可切到全站；B 面抽籤只抽 `memory`；A 面清單只列 `profile`。  
驗收：雙面文章不重複、單面文章不串面、舊文章不消失、載入失敗有退路。  
停止點：先保留現有視覺，只改資料與行為。

### 第 7 步：文章標記與探索中狀態

產出：文章頁的小型面向標記，以及探索中資訊塊。  
驗收：標記來自資料而非猜分類；缺欄位的舊文章不報錯；資訊塊在桌面與手機不搶正文焦點。  
停止點：不批次替舊文章補寫狀態。

### 第 8 步：視覺與互動定稿

產出：短暫翻面動畫、A 面較清晰的工作台語彙、B 面既有磁帶／記憶庫語彙。  
驗收：兩面仍像同一個人、不是兩個互不相干的網站；375px 手機無水平溢出；減少動態模式無動畫。  
停止點：先由作者本機試用，不部署。

### 第 9 步：整體驗收與履歷上線準備

產出：完整測試、操作說明、已知限制與部署前差異清單。  
驗收：執行 `npm run verify`、`git diff --check`、桌面與手機實際瀏覽器驗收；檢查兩個入口、搜尋、抽籤、返回、canonical、sitemap 與 404。  
停止點：取得作者明確部署授權後才部署；把 `/profile/` 放入履歷也應在實際部署驗收後進行。

## 10. 必須通過的驗收矩陣

| 案例 | A 面 | B 面 | 全站搜尋 | 直接網址 |
|---|---|---|---|---|
| `profile` 文章 | 看得到 | 不主動出現 | 一筆 | 可開啟 |
| `memory` 文章 | 看不到 | 看得到／可抽到 | 一筆 | 可開啟 |
| `profile + memory` 文章 | 看得到 | 看得到／可抽到 | 仍是一筆 | 同一網址 |
| 缺少欄位的舊文章 | 看不到 | 維持現況 | 一筆 | 維持現況 |
| 私人文章或私人資料 | 看不到 | 看不到 | 不存在 | 不產生公開網址 |
| 站務文章 | 視策展明確加入 | 不進隨機 | 可依既有規則找到 | 維持原網址 |

另外逐項驗證：

- `/profile/` 從履歷直接進入時不依賴 cookie 或先前狀態。
- A 面切 B 面、B 面切 A 面、重新整理與分享網址結果一致。
- 同一篇雙面文章不產生兩份 HTML、兩個 canonical 或兩筆搜尋結果。
- 搜尋切換到「全部公開內容」後，單面內容都能找到。
- B 面返回隨機文章時仍恢復原抽籤狀態。
- 現有 265 篇文章的網址、日期與正文不因分類而改變。
- 既有 `microblog.json` 每筆 `id` 保持不變；若新增公開項目，依既有 ID 工具流程處理。
- 沒有部署，除非作者針對部署另行明確授權。

## 11. 風險與防呆

| 風險 | 防呆方式 |
|---|---|
| 把 B 面誤當秘密空間 | 介面與說明都稱「另一面」，不稱私人；私人內容不進建置 |
| 同一篇文章複製兩份 | 只用 `surfaces` 引用同一 post；測試 canonical 與索引唯一性 |
| 舊文章突然出現在履歷入口 | 缺少欄位預設 `memory`；`profile` 必須明確標記 |
| 不同產生器各自判斷造成分歧 | 所有產生器共用同一個 surface 正規化工具 |
| A 面過度像制式作品集 | 現行以真實文章活動熱力圖與完整文章庫呈現，不用技能百分比、假進度條或空泛自評 |
| A 面內容太多 | 首頁只顯示最新活動年份熱力圖與所選日期明細；完整內容放次層文章庫 |
| 學習資料意外把 B 面文章帶入 A 面 | 學習項目 surface 必須是連結文章 surface 的子集合 |
| JavaScript 失敗後無法切面 | 使用真實網址與普通連結；JS 只負責增強動畫和互動 |
| 履歷連結打到 B 面 | 履歷只使用完整 `/profile/` 網址，部署驗收時逐字核對 |

## 12. 完成定義

只有同時符合以下條件，雙面部落格才算完成：

1. 履歷讀者從 `/profile/` 能看見工作／學習文章的活動分布，並在 `/profile/articles/` 瀏覽與篩選完整內容。
2. 作者從 `/` 仍能用原本喜歡的隨機方式回到自己的記憶。
3. 同一篇文章可以在 A、B 兩邊被找到，但永遠只有一份正文與一個網址。
4. 搜尋、抽籤、清單與選單對面向的理解一致。
5. 私人內容不是被藏起來，而是完全沒有進入公開建置。
6. 原有文章、網址、日期、microblog ID 與未提交修改均獲保留。
7. 完整自動測試與實際桌面／手機驗收通過，且部署另經授權。
