# 雙面部落格驗收與回復規則（WBS 0.3）

版本日期：2026-09-25（Asia/Taipei）
適用範圍：雙面部落格 WBS 0.1 起的每一個工作包。
前置文件：[施工基準](dual-surface-blog-baseline.md)、[路由與內容樣本](dual-surface-blog-samples.md)、[施工 WBS](dual-surface-blog-wbs.md)。

本文件只定義施工、驗收、留證與回復方法。A/B 樣本仍只是規劃驗收角色；內容公開、面向歸類、首頁文案及部署仍依 WBS 的 HOLD 確認點處理。

## 1. 每個工作包的共同流程

### 進場前

1. 閱讀根目錄 `AGENTS.md`、本工作包及相依工作的驗收條件；需要時參照本規則、施工基準與固定樣本。
2. 以唯讀方式記錄 `git status --short --untracked-files=all`、HEAD 與本工作包預計觸及的路徑。與 [0.1 Git 快照](dual-surface-blog-baseline.md#git-與工作樹基準) 比較，將新出現的修改視為作者工作，除非有證據確認為本工作包產物。
3. 逐檔檢視預計編輯檔案的現況和差異。檔案已含作者修改時，採最小、局部編輯；不能安全分辨所有權或改動邊界時，停止該檔案工作並回報。
4. 核對該工作包的前置依賴、作者決策是否已核准、測試方式與可回復範圍。未到依賴或決策未定時只做明確允許的盤點，不先寫入內容或程式。
5. 選擇最小目標驗證；程式工作完成後再依風險執行所需回歸／整體驗證。不要為純文件盤點建置網站。

### 完成前

1. 檢查每個產出與承諾的驗收逐項相符，記錄未完成、例外、未知及未核准項目。
2. 執行與修改類型相稱的驗證及 `git diff --check`。測試未執行或未通過，就不能將工作包標為完成。
3. 再次檢查 Git 狀態與實際差異；分清本工作包新增／修改的檔案、進場已有修改，以及工作期間新出現的其他檔案。
4. 核對本工作包新增的文件連結、生成頁或資料輸出；不可把存在的舊 `public/` 快照說成最新建置結果。
5. 在 `docs/personal-navigation-progress.md` 寫下工作包、實際變更、驗證證據、未完成事項、下一 WBS ID 及部署狀態。
6. 未經本次明確授權不部署；完成一個工作包即停止，不順手開始下一包。

### 證據記錄格式

每輪進度至少記錄下列欄位；沒有適用值時寫「不適用」或「未知」，不猜測：

```text
日期／時區：
WBS ID／名稱：
進場 HEAD：
進場 Git 狀態與需保護路徑：
實際修改檔案：
未修改但核對的來源／路由：
執行的命令或手動驗收：
結果（exit code、數量、URL、裝置尺寸、錯誤）：
與基準相比的差異：
未完成／未知／HOLD：
部署狀態：未部署／已依當次授權部署
下一 WBS ID：
```

命令輸出若有個人資料或敏感內容，只保存足以證明結果的摘要、識別碼與檔名，不複製敏感原文到公開文件。

## 2. 修改類型最低驗收矩陣

此表是最低門檻；個別 WBS 的條件更嚴格時，以較嚴格者為準。

| 修改類型 | 最低驗收 | 不能據此宣稱的事項 |
| --- | --- | --- |
| 文件／規劃 | 逐項核對需求、標題與相對連結；檢查日期、未知值和 HOLD 沒有被寫成已確認；檢查新增文件尾端空白及 `git diff --check`。 | 不代表程式已實作或生成網站已更新。 |
| 資料契約／驗證器 | 覆蓋 `profile`、`memory`、雙面、舊文章缺欄位、空值、錯字、錯誤型別及重複值；檢查錯誤能指出來源檔和欄位；確認舊文章解讀與預期相符。 | 單元測試通過不代表所有產生器、公開輸出已遵守契約。 |
| 文章 front matter／批次歸類 | 僅依作者核准清單；逐檔核對新增欄位及允許值；比對正文、日期、更新日期、permalink、既有 microblog ID 或其他受保護欄位未改；未確認案例維持未改。 | 不能由分類、標籤、檔名、AI 判斷或本文件的驗收角色推定 A/B 資格。 |
| 產生器／資料服務 | 執行目標單元測試及相關回歸；以小型固定 fixture 驗證新增、缺漏、錯誤與去重情形；建置後檢查索引／JSON 欄位、項目數、ID、URL、警告及引用資料一致性。進入整合里程碑時執行 WBS 要求的 `npm run verify`。 | 資料層通過不代表畫面、鍵盤、手機及無 JS 行為已通過。 |
| 版型／前端互動 | 目標回歸測試和網站檢查；檢查直接路由、重新整理、普通連結、返回與開新分頁；瀏覽器驗收桌面與窄手機，檢查鍵盤／焦點、無 JavaScript 基本路徑、錯誤／空狀態、無水平溢出及主控台錯誤。動畫另檢查減少動態偏好。 | 桌面截圖正常不代表無障礙、行動版或無 JS 完整。 |
| 隱私邊界／公開資料搬移 | 搬移前保存作者核准項目清單及可恢復來源；逐項確認公開／去識別／私人決策；生成後在 HTML、JSON、XML、索引、sitemap 及來源複製輸出搜尋核准測試字串；確認私人資料不因 CSS、搜尋或面向篩選而留在公開產物。 | 搜尋引擎不收錄、選單不顯示、頁面不連結不等於資料已私有。 |
| 瀏覽器驗收／發布候選 | 使用固定路由與內容樣本走完預定旅程；記錄瀏覽器、viewport、輸入、URL、預期與實際結果、主控台錯誤；手機至少核對 WBS 指定尺寸及無溢出；確認驗收後停止由本輪啟動的服務或明確交接。 | 本機驗收不代表部署成功或線上快取已更新。 |
| 部署／線上驗收 | 部署前取得當次明確授權，記錄發布候選 commit／工作樹差異、驗證結果、目標環境及回復方案；部署後核對主要入口、canonical、代表文章、搜尋／JSON 資料與錯誤狀態，保存時間和 HTTP／瀏覽器結果。 | 先前的部署授權不延伸到新版本；部署授權也不自動包含回復線上服務。 |

| 樣本 | 來源及目前識別 | 相關驗收 |
| --- | --- | --- |
| A 面候選工作文章 | 「工作知識系列 01」，目前 URL `/work/from-real-work-to-features/`；來源見 [樣本清單](dual-surface-blog-samples.md#規劃驗收角色a-面候選文章) | 若後續獲核准，A 面卡連回此既有單一 URL；日期、更新日、分類及正文保留。 |
| B 面候選歌曲 | `source/_posts/歌曲推薦/歌曲推薦-sailing back to you.md`；目前路由在 [樣本清單](dual-surface-blog-samples.md#規劃驗收角色b-面候選文章) | 若後續獲核准，隨機抽籤可包含該 B 候選，歌曲封面、分類與既有 URL 不變。 |
| 雙面候選＋learning 去重 | 文章 `/learning/website-quality-testing-roadmap/` 與 `reading-topic-07` 同 URL；見 [配對樣本](dual-surface-blog-samples.md#規劃驗收角色雙面候選與-learning-去重配對) | 索引不得重複文章；學習附註合併後仍保留加入日期與文章發表／更新日期的區別。 |
| 站務文章 | `source/_posts/部落格改版規劃.md`；見 [樣本清單](dual-surface-blog-samples.md#規劃驗收角色站務文章) | 隨機資料維持排除站務文章；檢查可訪問 URL 不變，不因排除抽籤而誤刪文章。 |
| microblog 碎碎念 | `micro-56bb6eec75c50bcd`，入口 `/status/#micro-56bb6eec75c50bcd` | 既有 ID 不變、錨點可定位；日期維持紀錄日語意。 |
| learning 題目 | `reading-topic-07`，位於 `source/reading-desk.yml` | 草稿夾入口可找到題目並回到同一文章 URL；索引只一筆，日期語意為加入草稿夾。 |

若來源文章、microblog ID、日期、URL 或 learning 配對有變動，先停用該筆舊預期、唯讀查明原因並更新樣本文件／驗收記錄；不能為了讓測試通過而自動改寫來源。

## 4. 停止條件與 HOLD 處理

遇到下列情況，停止該工作包中受影響的修改，保留現場並在進度文件記錄證據與待決問題：

- 不確定內容能否公開，或可能包含他人、公司、客戶及未公開專案資料。
- 候選文章需要大幅改寫才適合 A 面，或必須由作者判斷公開範圍、成熟度與適用邊界。
- 為施工必須改動既有 permalink、日期、正文或持久 microblog ID。
- 搜尋、抽籤、首頁、清單等產生器對同一筆內容作出不同面向判斷，或要求同一正文產生兩個 URL。
- 目標測試、整體建置、連結稽核或公開輸出稽核失敗且未定位／修正。
- 工作需要登入、伺服器權限、第三方傳送或其他超出 WBS 的能力。
- 下一步會造成未經授權的外部改變，例如部署、刪除線上內容或回復服務。
- 發現本輪差異與使用者既有修改重疊，且無法安全拆分。

HOLD 代表「此決定由作者保留」，不代表可自行採最方便的預設：

- WBS 2.2：內容公開、去識別或轉私人由作者逐項確認；工程可先完成清單，不搬移未確認內容。
- WBS 3.2：首批文章的 A／B／雙面歸類由作者核准；不得批次寫入 front matter。
- WBS 5.1：A 面定位句、路徑與排序由作者確認；工程可先準備頁面骨架，不代定公開文案。
- WBS 9.5：A/B 名稱、切換控制與視覺語氣由作者確認；未決時不宣告視覺定稿。
- WBS 10.7：部署與否由作者針對發布候選明確決定；未授權時停在本機發布候選。

遇到 HOLD，可繼續不依賴該決定的唯讀盤點、測試工具或已核准部分，但不能用模擬樣本代替作者確認，也不能把未確認項標為完成。

## 5. 測試失敗處理

1. 保存失敗命令、時間、退出碼、完整錯誤訊息或可追溯輸出、工作樹狀態與重現條件；錯誤輸出含私密資料時保存遮蔽後證據。
2. 停止擴大工作範圍。唯讀定位失敗是環境、既有基準、測試資料、程式還是公開輸出造成；不得先刪測試、放寬斷言或改寫基準來消除失敗。
3. 若失敗明確由本工作包修改造成，且修正不碰作者既有工作與 HOLD 項目，只修正該範圍並重跑失敗案例。
4. 失敗案例通過後，再跑相關回歸；工作包或里程碑要求整體驗證時，最後執行完整驗證並再次保存輸出。
5. 仍失敗、原因未知、修正會超出本工作包，或必須跨入使用者決策時，停止並回報。保留失敗證據與安全可檢視的工作狀態，記為未完成，不部署。

## 6. 檔案級回復原則

- 回復範圍只能是本工作包明確新增或修改、且可證明由本輪造成的差異；以進場狀態、修改紀錄和逐檔 diff 作判斷。
- 任何檔案在進場前已有未提交修改時，只能考慮撤回本輪清楚可分離的行；不能將整個檔案還原成 HEAD，也不能覆蓋作者內容。
- 同一檔案的差異無法可靠分離、擁有權不明或期間有其他作者修改時，不執行回復；保留現狀並請作者決定下一步。
- 新增文件或測試檔若為本工作包產物，也先確認在本輪後未被作者修改；所有權不明時保留，不刪除。嚴禁刪除未追蹤使用者檔案。
- 禁止使用 `git reset --hard`、`git checkout --`、`git clean` 及任何以整個工作樹／資料夾為對象的清理操作。不得使用廣域批次回復或刪除命令。
- 回復前記錄要回復的檔案、已知本輪差異與原因；回復後檢查該檔、相關測試與 `git status`，並在進度紀錄說明結果。此規則本身不授權回復，本次 WBS 0.3 不回復任何檔案。

## 7. 部署與線上回復界線

- 本機修改、建置、預覽與部署是不同操作。部署前必須向作者呈現具體發布候選、驗證結果、目標及預計變更，並取得針對該次候選的明確部署授權。
- 過往授權不沿用；部署授權不等於授權未來另一次部署、資料刪除、資料庫／DNS 變更或線上回復。
- 部署前確保回復方式、發布識別和外部依賴狀態已查明；若無可驗證回復路徑，先停止發布並回報，不自行承諾可復原。
- 部署後先做唯讀健康檢查與固定 URL 驗收，再決定是否需要額外處理。任何會改變線上狀態的回復操作都須取得當次明確授權；獲准後只回復該發布造成的外部變更，並再次驗證。
- 不把本機 Git 檔案回復規則套用成線上操作，也不以本機版本成功建置推論部署、CDN 或搜尋引擎已更新。

## 8. 每輪 progress 範本

```markdown
## YYYY-MM-DD，雙面部落格 WBS X.Y：工作包名稱（完成／未完成，未部署）

- 進場基準：HEAD `<hash>`；Git 狀態與受保護差異：`<簡述或基準文件連結>`。
- 本輪修改：`<檔案與內容>`；未修改但核對：`<來源／路由>`。
- 驗證：`<命令或實際操作>`；結果：`<退出碼、數量、URL、裝置及錯誤>`。
- 未完成／未知／HOLD：`<事項；沒有則寫無>`。
- 部署：未部署；若有部署，附當次授權和發布識別。
- 下一步：WBS `<ID>` `<名稱>`。
```

進度紀錄只描述實際發生的工作。沒有執行的測試不能寫通過，沒有驗收的產物不能標完成；遇到失敗時保留失敗結果及停止原因。
