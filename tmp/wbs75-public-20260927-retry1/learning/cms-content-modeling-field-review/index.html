CMS 前後台理解｜前後台欄位對照與規格審查｜學習筆記

我整理 CMS 前後台、內容建模與規格審查，先建立專案討論前可以對照的工作手冊。

這是一篇公開的持續學習筆記，先把我對 CMS 前後台、內容建模、動態套版與規格審查的理解整理在同一個地方。現在的版本比較像一份 PM 在專案討論前可以拿來對照的工作手冊，之後會再補上實際案例、欄位規格與查證過的參考資料。

資料狀態：研究整理、持續修正

以下內容是目前的理解與工作假設。書籍、文章與業界方法的說法，還需要回到原始資料核對；實際專案仍應依需求、技術環境與團隊約定確認，不能只靠這份筆記直接決定規格。

CMS 系統架構與建置全貌指南

從「功能執行」升級為「全站架構思維」

專案經理在 CMS 專案會議中感到跟不上討論或失焦，常常不是因為不理解某個按鈕，而是過早陷入局部視覺或單一功能，沒有同時看見內容如何建立、儲存、分類、發布、被套版，以及最後如何呈現在不同頁面。

我目前把這個問題整理成兩條主線：

  • 系統連貫性：同一份內容是否能被不同頁面、模組與渠道正確使用？
  • 資料生命週期：內容從建立、審核、發布、修改到下架，過程中的狀態與責任是否清楚？

這篇筆記希望先建立一個由上而下的觀察框架，再慢慢把它轉成實際可用的欄位對照與規格審查表。

一、核心概念的操作型定義

1. 資料與內容建模

內容建模是把業務需求抽象成獨立於視覺呈現之外的結構，包括實體、欄位、關聯與驗證規則。換句話說，先決定「這是什麼內容」以及「這份內容需要保存什麼資料」，再討論它要在哪個頁面呈現。

目前先用以下四個部分理解：

  • 實體／內容類型：例如公告、文章、活動、人物或下載資源。
  • 屬性／欄位：例如標題、摘要、封面、日期、作者與狀態。
  • 關聯：例如文章與分類、活動與報名表、公告與附件之間的關係。
  • 驗證規則：例如必填、字數上限、格式、權限與空值處理。

這裡先記下兩個參考方向，之後需要再核對內容與引用範圍：

  • Web Content Management: Systems, Features, and Best Practices：把內容管理系統放回內容模型與管理流程中理解。
  • Designing Connected Content：從 Content-First 的方向思考內容如何被不同介面重複使用。

2. 資訊架構與分類法

資訊架構不只是把選單排得好看，而是讓使用者能找到內容，也讓系統知道內容之間如何組織。暫時先拆成四個部分：

  • 組織系統：內容依什麼規則分組。
  • 標籤系統：用哪些詞描述內容。
  • 導覽系統：使用者如何從入口走到內容。
  • 檢索系統：搜尋、篩選與排序如何運作。

分類、標籤、URL 與搜尋結果其實會互相影響，因此不能只在切版階段才決定。參考方向是 Information Architecture for the World Wide Web，之後要再把書中的架構概念對照到實際 CMS。

3. 前端切版與介面元件化

前端切版是把視覺設計轉成語意化 HTML、響應式斷點與可重用的 UI 元件。重點不只是「畫面看起來一樣」，還包括：

  • 元件是否有清楚的資料輸入與輸出？
  • 不同內容長度是否會破壞版面？
  • 圖片、表格、按鈕與表單在不同螢幕上是否仍然可用？
  • 元件是否具備基本的無障礙語意？

這部分先以 Atomic Design Methodology 作為理解介面層級的參考，但仍要小心：分類方法本身不是目的，真正重要的是元件能否穩定地被重複使用。

4. 動態套版與樣板引擎

動態套版可以先理解成：樣板提供呈現結構，內容模型提供資料，樣板引擎再依照條件、迴圈、資料管道與快取規則輸出頁面。

因此前後台對照時，不應該只問「這個欄位在後台放哪裡」，還要問：

  • 這個欄位會被哪個模板使用？
  • 空值時前台要隱藏、顯示預設文字，還是改用其他欄位？
  • 內容是純文字、Markdown、富文本，還是結構化區塊？
  • 這個欄位在列表頁與詳細頁是否有不同的呈現規則？

二、建站者視角：全站工程發問矩陣

維度 1：資料邊界與屬性約束

  1. 內容是純文字、結構化欄位，還是可能產生雜訊 HTML 的富文本？
  2. 標題、摘要與內文的字數上下限是多少？
  3. 欄位為空時，前台的 fallback 邏輯是什麼？
  4. 圖片與影音的長寬比、格式、容量與替代文字如何限制？
  5. 是否有自動轉檔、縮圖、壓縮與檔案版本管理？

維度 2：分類法與實體關聯

  1. 分類與標籤是一對多還是多對多？
  2. 是否需要支援巢狀層級？層級上限與管理責任是什麼？
  3. 相關文章是透過標籤自動查詢，還是由小編手動綁定？
  4. 關聯內容被下架、刪除或改名時，前台如何處理？

維度 3：版型映射與元件重用

  1. 全站頁面能否收斂成少數幾種內容類型與模板？
  2. 不同頁面的卡片是共用帶參數的元件，還是各自維護結構？
  3. 同一份資料需要在哪些頁面、搜尋結果或推薦模組出現？
  4. 元件的變體是由資料欄位控制，還是由編輯者選擇？

維度 4：狀態容錯與例外處理

  1. 搜尋或篩選結果為零時，要顯示什麼 Empty State？
  2. 文章是否有草稿、預約發布、已下架、權限限制與版本回溯？
  3. 富文本是否有 HTML 白名單與淨化機制？
  4. 外部連結失效、圖片不存在或欄位缺漏時，前台要如何降級？

三、AI 時代的漸進式結構化釐清法

我目前把 PM 使用 AI 協助釐清規格的流程拆成四步。AI 可以幫忙找出遺漏與衝突，但最後仍要由人確認業務語意與交付責任。

步驟 1：全域實體提取

先把網站類型、頁面清單、既有需求與內容來源交給 AI，請它從系統架構角度提取核心內容類型，並整理實體之間的一對多、多對多關係。

重點不是讓 AI 立刻產出資料庫，而是先避免每一頁都被當成完全獨立的功能。

步驟 2：階層與分類法對齊

針對已確認的內容類型，逐一確認哪些適合用分類，哪些只需要標籤，以及是否存在跨實體的動態引用。這一步也要檢查是否因為追求彈性而產生過度複雜的架構。

步驟 3：微觀欄位與邊界探勘

針對某一個內容類型，請 AI 扮演技術主管，提出需要向客戶確認的型態、Fallback、字數、富文本與例外處理問題。這可以作為會議提問清單，但不能直接當成客戶已同意的規格。

步驟 4：規格落地與交付閉環

最後把討論結果整理成單一真實來源的規格表：

欄位名稱 資料型態 必填／選填 限制條件 空值處理 後台元件
待補 待補 待補 待補 待補 待補

這張表之後應該要能同時交給 PM、設計、前端、後端與內容編輯者使用，讓每個人看到的是同一套欄位定義。

四、客戶語言與系統架構語言

客戶需求 容易誤解的焦點 建站者真正要確認的問題
首頁想放最新公告，點進去可以看內容 輪播特效、標題顏色 公告是否為獨立 Content Type？排序與內頁模板是什麼？
文章底部希望推薦相關文章 推薦三篇還是四篇 依標籤自動查詢，還是由小編手動綁定？不足時如何補齊？
下載專區要放很多檔案 下載按鈕圖示 支援哪些格式？檔案是文章附屬，還是全域資產庫？
首頁區塊希望小編自由拖拉排序 直接答應可以拖拉 區塊有幾種？資料是動態查詢還是靜態填入？版本如何維護？

這個轉換的價值，不是把客戶的話翻成艱深術語，而是把一句看似單純的需求拆出它會影響哪些資料、模板、權限與維護成本。

五、核心參考資料

  1. Web Content Management: Systems, Features, and Best Practices — Deane Barker。
  2. Designing Connected Content — Mike Atherton、Carrie Hane。
  3. Information Architecture: For the Web and Beyond — Louis Rosenfeld、Peter Morville、Jorge Arango。
  4. Atomic Design Methodology — Brad Frost。

後續查證與實作清單

  • 找一個實際 CMS 專案，把前台頁面反推成內容類型與欄位。
  • 選一個內容類型，完成前台、後台、資料庫與 API 的欄位對照表。
  • 補上欄位空值、字數限制、圖片規格與發布狀態的例外處理。
  • 核對參考書籍中對 Content Modeling、IA 與 Component 的原始定義。
  • 把這篇筆記中的「應該」逐項改成已有來源或專案決策支持的說法。

預先收集：把欄位變成可交付的規格

  1. Content models｜Contentful Help：把內容模型理解成內容類型、欄位與彼此參照的總體結構，也提供視覺化建模與 API 建模的入口。
  2. Schemas and forms｜Sanity Docs：清楚區分 schema、document type 與 field type，適合對照「後台欄位」和「內容實體」不是同一層概念。
  3. Sanity TypeGen：示範如何從 schema 與查詢產生型別，讓前後端在欄位名稱、資料型態與必要欄位上有可檢查的契約。
  4. OpenAPI Specification：補上 API 的 request、response 與 schema 描述，適合拿來把前台顯示欄位和後端實際回傳欄位對起來。

我的參考意見

這幾份資料共同支持一個很實用的判斷：CMS 欄位不是切版細節，而是內容模型、API 契約、編輯流程與前台呈現的交界。PM 可以先做一張單一真實來源的欄位表，至少包含「顯示名稱、API key、資料型態、必填／選填、驗證規則、空值處理、前台使用位置、負責人與範例值」。如果這些資訊沒有文件或決策紀錄，前端、後端與 PM 都只能靠猜，工時自然不可能估得準。
