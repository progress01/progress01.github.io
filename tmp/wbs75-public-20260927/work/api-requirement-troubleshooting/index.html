工作知識｜API 需求排查：從前台現象回到資料來源

我在排查 API 資料異常時，先回頭追查資料來源、處理流程與最後出現差異的層次。

這篇把工作事件去脈絡化後留下的知識紀錄。公司、人物、機構、網址、檔名、精確時間與特定資料內容都不放進來，只保留這次排查過程中可以移植到其他工作的思考方式。

這次處理的需求和 API、批次更新、排程與外部資料來源有關。表面上看起來像是前台資料沒有更新，但真正需要釐清的問題其實是：

資料從哪裡來？中間經過哪些處理？最後是在哪一層出現差異？

一開始容易走錯的方向

看到前台畫面、附件內容或使用者回報異常時，很容易一路追著前台找：

  • 這個畫面是不是沒有更新？
  • 這個連結是不是指錯地方？
  • 是不是需要新增一支排程？
  • API 是不是沒有把最新資料帶回來？

這些問題都可以問，但如果一直停留在前台，就很難知道資料實際上是怎麼形成的。

這次最重要的修正是：

遇到 API 需求時，不能只看前台結果；要先建立從資料來源到前台的完整路徑。

前台只是最後看得到的結果，不一定是問題發生的位置。

先畫出資料流，再開始判斷

這類需求可以先照下面的順序拆開：

外部資料來源
→ 後台資料或附件
→ 排程／批次更新
→ API
→ 前台查詢與下載

每一層都要問一個不同的問題：

層次 要確認的問題 可以留下的證據
外部資料來源 原始資料是否真的已更新？來源位置有沒有變動？ 來源網址、檔案版本、更新紀錄
後台資料或附件 系統實際存的是哪一份資料？欄位和檔案在哪裡？ 後台位置、欄位、附件名稱
排程／批次更新 是否已有更新機制？多久執行？執行了什麼範圍？ 排程設定、原始碼、執行紀錄
API 回傳的是哪一層資料？是否已重新抓取或只是轉送舊資料？ API 路徑、回應內容、請求時間
前台 使用者最後看到的內容是否和後台一致？ 頁面、下載檔、畫面擷取

這樣做是為了避免因為某一個人的口頭描述，就直接假設問題一定在前台、API 或排程其中一層。

這次最容易混淆的三件事

1. API 有問題，和來源資料有問題，不是同一件事

如果 API 正確地把上游提供的資料帶回來，但上游檔案本身是舊的、內容重複的、網址已經更換，前台看起來仍然會是錯的。

因此排查時不能只問：

API 有沒有更新？

還要問：

API 更新的資料，來源本身是不是正確而且最新？

只有把來源、API 回傳與前台結果放在一起比較，才有機會判斷責任邊界。

2. 確定有排程，和知道排程怎麼運作，是兩件事

口頭上說「以前有排程」時，至少還有幾個問題沒有回答：

  • 排程現在是否仍然存在？
  • 它實際多久執行一次？
  • 每次執行會更新全部資料，還是只有部分資料？
  • 排程抓的是固定網址、檔案清單，還是某個 API？
  • 執行成功代表資料內容真的改變了嗎？

所以「有排程」不能直接等於「資料一定會更新」。排程設定、執行紀錄與實際檔案內容要分開確認。

3. 系統標示的時間，不一定是資料真正的更新時間

畫面上可能有建立時間、抓取時間、處理時間或顯示時間，但這些不一定代表外部資料最後修改的時間。

如果檔案本身沒有可靠的更新日期，就不能只靠畫面上的時間判定資料是否真的更新。這時要改用版本差異、內容比對、來源頁面或實際下載結果交叉確認。

真正有用的排查方法

先找到一筆已知異常的資料

隨機點資料有時候只能證明「某一筆看起來正常」。更有效的方式是先找到已經被回報、而且可以明確描述差異的資料，再從這一筆往回追：

  • 前台顯示了什麼？
  • 後台對應到哪一筆？
  • API 回傳了哪一份？
  • 外部來源目前提供什麼？
  • 哪一層和其他版本不一致？

已知異常資料像一個定位點，可以讓排查從「猜測」變成「比對」。

在任何更新前先留下原始狀態

這次也讓我更確定，處理資料更新時，最容易失去的是「更新前的證據」。如果接到需求時資料已經被更新，就很難回頭證明原本到底是什麼狀態。

之後至少可以保留：

  • 異常頁面的畫面擷取。
  • 來源頁面與檔案位置。
  • API 回應或下載檔案。
  • 觀察到的時間與版本資訊。
  • 哪些資料已經更新、哪些還沒有更新。

這些紀錄不是要把事情寫得很複雜，而是避免之後只能依靠記憶或口頭轉述。

如果問題可能不只一筆，先考慮完整更新

當回報顯示不只一個資料項目有問題時，只修正單一筆可能會留下更多沒有被看到的錯誤。

這時要先確認：

  • 上游是否已經整批更新？
  • API 是否能執行完整重抓？
  • 更新會不會影響其他資料？
  • 更新後要用哪些已知異常資料驗證？

重點不是每次都要整批更新，而是要先判斷問題的範圍，再決定單筆修正或全面刷新。

為什麼原始碼與資料流文件很重要

如果只知道前台畫面，不知道後台位置、排程設定與資料來源，遇到異常時就只能一直問人，或從結果反推系統。

反過來，如果一開始就取得排程原始碼、API 欄位說明與資料來源位置，就能比較快回答：

  • 哪些事情系統本來就會做？
  • 哪些事情其實不需要重新開發？
  • 哪些設定只是承辦或使用者記憶中的版本？
  • 哪些問題來自上游資料，而不是我們的程式？

原始碼不只是開發資產，也是排查問題時的系統地圖。越晚拿到，越容易在資訊不完整的情況下做出錯誤判斷。

可以留下來的工作原則

這次我想保留的，不是某個特定系統的解法，而是下面幾個原則：

  1. 先確認資料流，再決定要改哪裡。 不要看到前台異常就直接修改前台或新增 API。
  2. 把口頭資訊當成線索，不當成現況。 排程週期、資料是否更新、誰負責來源，都要用設定或紀錄確認。
  3. 先找已知異常，再做前後比對。 一筆明確的錯誤資料，比大量模糊的正常資料更有定位價值。
  4. 在更新前留下證據。 否則更新完成後，可能只剩下「現在看起來正常」可以證明。
  5. 分開判斷來源、後台、API 與前台。 某一層修好了，不代表整條資料鏈都正確。
  6. 先取得程式碼、欄位與排程資料。 有資料流圖，就不必只靠印象或猜測排查。

下次遇到類似需求，我會先問什麼

  • 這次需求是要新增機制，還是既有機制沒有正常運作？
  • 前台看到的資料，對應到後台哪個欄位或檔案？
  • API 是直接回傳後台內容，還是會重新抓取外部來源？
  • 外部來源最後一次更新的證據在哪裡？
  • 排程的設定、執行頻率與實際更新範圍是什麼？
  • 目前的異常是一筆、部分資料，還是整批資料？
  • 在任何更新前，有沒有留下可以比較的原始狀態？

這些問題要先後問，比一開始就問「要不要改 API」更重要。

目前的結論

這次讓我最清楚的一件事是：

處理 API 需求時，真正要追的不是某個畫面，而是資料如何一路走到那個畫面。

前台是現象，後台是系統中的位置，排程是時間與流程，外部來源是資料的起點，API 則是中間的傳遞方式。只有把這幾層放在一起，才不會被單一畫面、模糊記憶或錯誤歸因帶著走。

最後可以把這次的方法濃縮成一句話：

先畫資料流，先留原始狀態，再從已知異常往回追。
