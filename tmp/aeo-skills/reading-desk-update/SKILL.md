# 草稿夾／學習筆記更新

Use this skill only for the user's Hexo blog learning archive. The archive is a persistent accumulation library, not a temporary draft queue. Keep each record in the archive after publication; changing its state must not delete or move the record.

## Source of truth

- Repository: `C:\Blog\blog-1988`.
- Archive data: `source/reading-desk.yml`.
- Public learning notes: `source/_posts/實驗室/`.
- The generated `public/reading-desk.json` is a build artifact. Never edit it by hand; regenerate it with Hexo.
- Each topic and YAML item must have a stable, unique `id`; reuse the existing topic/item id when continuing a subject and never invent a replacement id because wording changes. Each item must have a valid `date`, `title`, `source`, `url`, `state`, and `note`. `date` means the date it entered the archive, not the latest edit date.
- `state` is exactly one of `collected`, `learning`, or `published`. It is not a relocation command. `resolved_date` is optional historical metadata only.
- A new note needs a valid permalink under `/learning/`, with YAML `url` exactly matching the Markdown permalink. Read current registered taxonomy from `source/_data/content-categories.yml` and `source/_data/content-tags.yml`; new notes use the primary registered tag `學習筆記`. Preserve existing additional tags rather than silently deleting them. For an existing note, preserve `date` and `permalink`; add `updated` only for substantive content changes with a reliable `Asia/Taipei` date, never for formatting or image conversion.

## Reading desk calendar meaning

- The calendar is a daily-addition reading log, not a cumulative unresolved-backlog heatmap.
- Each calendar date and its clicked detail list must show only items whose `item.date` is that selected date. Do not carry earlier open items into later dates.
- An item remaining `state: learning` keeps it in the permanent archive, but must not cause it to be counted again on subsequent calendar dates.

## Knowledge-content writing guardrails

When drafting or substantially revising an explanatory learning note, state the core question or claim early in a way that fits the note's purpose. Preserve the author's personal reasoning and label what is observed, inferred, or still hypothetical. For time-sensitive or technically checkable claims, use a reliable primary source that was actually read and place the source near the claim. Add scope or exceptions only when they change how the note should be applied. Do not add FAQ blocks just for AEO, invent `about`/`sameAs`/authority claims, or force an unrelated template; JSON-LD remains generated by the theme under the existing consistency rules.

## When adding a learning item

1. Read the current YAML and existing learning posts first. Reuse an existing topic when the subject belongs there; add a topic only when it is genuinely new, with a stable id grounded in supplied material rather than guessed fields.
2. Add one stable item under the topic in `source/reading-desk.yml`.
3. Create one directly published Markdown file under `source/_posts/實驗室/`; do not put it in `source/_drafts/`. New posts require a valid date and the primary `學習筆記` tag. Use the user's learning-note style and preserve the chosen permalink.
4. Make the YAML `url` exactly match the Markdown post's generated URL. The post should remain editable after it is published.
5. Do not duplicate an item when the user is continuing an existing subject. Find it by stable `id`, title, or URL and update the existing Markdown/YAML entry.

## When updating or completing an item

- Edit the existing Markdown file in place so its public URL and accumulated history remain stable.
- Update the YAML `note` and `state` when the learning stage changes. Keep the item in `reading-desk.yml` even when `state: published`.
- Only add `resolved_date` when the user wants a completion date recorded; never use it as a reason to remove the item from the archive.
- Do not change the reading-desk presentation layout for ordinary content updates. The page and its date view read from the YAML-generated JSON.

Edit an existing note and its YAML item in place; preserve unknown front-matter and item fields rather than rebuilding either from the new-note example. Keep `date` and `permalink` by default; if the user explicitly requests a correction, apply it and check the YAML URL and internal links. For formatting-only or image-conversion changes, keep any existing `updated`; for substantive content changes, set or add one `updated` using a reliable `Asia/Taipei` timestamp, without duplicate fields or moving it backward. If the user explicitly requests correction of an erroneous timestamp, follow that request and verify generated `dateModified >= datePublished`. If a hand-written `description` or `excerpt` exists, confirm it still represents the revised note and do not add either field just to satisfy this check. JSON-LD is generated by the theme; never paste it into a learning note. After generation, check `headline`, canonical URL, `datePublished`, `dateModified`, and `image` against the note's title, permalink, dates, and actual cover or representative image. See the [project Schema.org notes](<C:/Blog/blog-1988/Schema.org JSON-LD 實作手冊.md>) when needed.

## Verification and publication

For every content change, run `npm run verify` from the repository; it already includes clean/build/site checks. Confirm that:

- content validation passes;
- Hexo generates `reading-desk.json`;
- the generated dates are `YYYY-MM-DD` values;
- the expected learning items and `/learning/` URLs are present;
- the learning post itself is generated.

If verification is blocked or fails because of unrelated working-tree changes, report the actual command, failure, and affected files; do not claim pass.

If the request is to publish the change, deploy only after verification with `npm run deploy`; honor explicit publication authorization already given in the session without asking again. If a visual or interaction change is also requested, inspect the local page before deploying. Report the actual verification and deployment result; do not claim a page is fixed from source inspection alone.

## Response convention

When reporting an update, briefly state which item was created or edited, that it remains in the permanent archive, the verification result, and whether deployment succeeded. If a local server port is already occupied, use another port for validation and explain that only when relevant.
