# 工作知識部落格系列維護

Use this skill when the user wants to turn a work event, troubleshooting experience, project review, quotation lesson, publishing issue, or important work record into a public article in `C:\Blog\blog-1988`.

Do not use it for reading-desk learning topics, song posts, imported Blogger posts, or ordinary private diary entries. The work series is public-facing and should preserve transferable reasoning while removing identifying context.

## Non-negotiable series conventions

- Store work articles under `source/_posts/實驗室/` with a filename beginning `工作知識-`.
- Read the current registered taxonomy from `source/_data/content-categories.yml` and `source/_data/content-tags.yml`. New work articles use the registered category `工作知識` and primary tags `工作方法`, `重要紀錄`; do not invent a new work tag for an individual article. If the user explicitly asks for a third tag, check the registered tags and normalizer before adding it. Preserve existing additional tags.
- Use a unique permalink under `/work/<slug>/` and check for an existing post or permalink before creating a new one.
- For a new article, add the series presentation metadata:

  ```yaml
  cover: /images/work-knowledge-card.svg
  work_knowledge: true
  work_note: <short topic-specific note>
  longform: true
  ```

  `work_note` should be a short phrase suitable for the archive card, such as `資料流與問題排查` or `工期、利潤與隱形成本`. The theme renders it as `NOTE / ...`.
- The shared work cover reuses the same small 1988-style document card as the reading-desk visual at `source/images/work-knowledge-card.svg`: a dark blue note panel, dotted guide line, monospaced status labels, and orange/mustard accents. Do not add work-specific text to the image; identify work articles through the card's `WORK / 工作知識` label and `NOTE / <work_note>` instead. Create a different image only when the user asks for a new visual direction.
- Keep a valid event or source record date in `date`; a new article must have one. Existing articles preserve `date` and `permalink`. Add `updated` only when substantive material is added and a reliable `Asia/Taipei` date is available; do not invent it for formatting or image conversion, or move a historical record into today's archive merely because it was edited today.
- Edit an existing work article in place and preserve unknown front-matter keys and existing `cover`, `work_note`, and `longform` values; only add missing fixed fields. Keep `date` and `permalink` by default; if the user explicitly requests a correction, apply it and check internal links. For formatting-only or image-conversion changes, keep any existing `updated`; for substantive content changes, set or add one `updated` using a reliable `Asia/Taipei` timestamp, without duplicate fields or moving it backward. If the user explicitly requests correction of an erroneous timestamp, follow that request and verify generated `dateModified >= datePublished`. If a hand-written `description` or `excerpt` exists, confirm it still represents the revised body and do not add either field just to satisfy this check. JSON-LD is generated by the theme; never paste it into the article. The known shared `/images/work-knowledge-card.svg` is presentation-only and must be omitted from JSON-LD `image`; other SVG covers that represent article content may be used as `image` according to the generated template. Check generated `headline`, canonical URL, `datePublished`, `dateModified`, and any applicable `image` against the actual output. The work structured-data rule is documented in the [project Schema.org notes](<C:/Blog/blog-1988/Schema.org JSON-LD 實作手冊.md>).
- Do not update `source/reading-desk.yml` for ordinary work-knowledge articles. The reading desk is for ongoing reading and learning topics.

## Public de-contextualization

Before writing, separate the source conversation into observations, reasoning, and details that must not become public. By default, remove:

- names, employers, clients, agencies, institutions, project names, and identifiable roles;
- exact URLs, file names, timestamps, record identifiers, and uniquely identifying data;
- screenshots or copied text that could reveal the original case;
- credentials, internal paths, confidential numbers, and private correspondence.

Keep the mechanism and decision process: what looked wrong, which layers were compared, what evidence changed the diagnosis, what was learned, and what can be reused. Do not reproduce a chat transcript as the article. If adding general advice beyond the supplied record, label it as a supplement or frame it as a reusable checklist rather than presenting it as an observed fact.

## Article shape

Adapt the headings to the material, but usually include:

1. a short de-contextualized situation statement;
2. the main insight or mistaken assumption;
3. the reasoning or investigation path;
4. reusable methods, decision boundaries, or a checklist;
5. boundary conditions and risks;
6. a concise conclusion;
7. an `# 更新紀錄` section with the original record date and later additions.

Prefer a coherent explanation over a line-by-line transcript. Preserve the user's own uncertainty when it matters, and distinguish a confirmed conclusion from a hypothesis that still needs verification.

## Existing-site maintenance

Before editing, inspect the current work posts, theme card logic, and registered metadata. Preserve unrelated working-tree changes. If the work card implementation is missing, the required behavior is:

- work posts appear in the archive/home feature card;
- the card uses `WORK / 工作知識`;
- the work card reuses the reading-desk document panel, uses the warm 1988 paper palette, and displays `NOTE / <work_note>`;
- reading-desk learning cards keep their existing `LAB / 學習筆記` presentation.

Do not create duplicate category or tag definitions. If a tag is not registered in `source/_data/content-tags.yml`, add it only when the user explicitly wants a new series tag; otherwise use the fixed work tags and preserve any existing aliases in `source/_data/content-tags.yml`. The shared `scripts/tag-taxonomy.js` module supplies the taxonomy used by the normalizer and content check.

## Verification and stopping point

After every content change:

1. Run `npm run verify` from `C:\Blog\blog-1988`.
2. Confirm the article output exists under `public/work/<slug>/index.html`.
3. Confirm the work category and both fixed tag pages are generated, and the article output contains the work cover and note.
4. Scan the source article for accidentally retained identifying details from the supplied material.
5. Review `git status --short` and leave unrelated changes untouched.

If verification is blocked or fails because of unrelated working-tree changes, report the actual command, failure, and affected files; do not claim pass.

Do not deploy or publish externally unless explicitly authorized; honor authorization already given in the session without asking again. Report the actual verification and publication result without claiming deployment when it did not occur.
