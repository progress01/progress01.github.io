工作知識｜把官網改版包裝成遊戲：有趣的是探索，不是資料庫

發表於 2026-02-26 更新於 2026-09-15 分類於 工作知識 文章字數： 4.9k 所需閱讀時間 ≈ 4 分鐘

這是我第一次開始幫忙想像一個網站會長什麼樣子：我當時還是新手，先被漂亮的參考網站吸引，後來才發現真正困難的是把模糊的想像拆成資料流、瀏覽路徑與能驗證的工作。

這是一篇把一段未採用的工作構想去脈絡化後留下的紀錄。原本的討論從「官網改版要怎麼推廣」開始，後來延伸到尋寶、情境任務、點擊解謎、低成本工具與單人 2D 探索遊戲。最後沒有真的導入，因此本文不把它當成成功案例，而是回頭整理：這個想法解決了什麼問題、哪些地方只是推測，以及如果再做一次，應該先驗證什麼。

第一次開始想像網站：新手先學會把害怕拆開

我第一次參與網站改版的前期討論時，最直接的感覺其實不是興奮，而是害怕。

我知道網站應該要變得更清楚、更好用，也能看出一些參考網站的畫面很漂亮，但我還沒有辦法在腦中想像：一個網站到底是怎麼從現在的樣子，走到最後可以交付的樣子？會議裡出現的技術名詞越多，我越容易覺得自己好像什麼都不懂，也不知道下一步能做什麼。

後來我才慢慢分辨出來，當時缺的不是一張更漂亮的參考圖，而是一個能把全貌拆開的順序。

我需要先知道：現在的網站有哪些內容、誰會使用、每種人進來想完成什麼事情、資料從哪裡來、經過誰確認，最後又要在哪裡被看見。這些問題還沒有回答以前，直接討論顏色、版型或互動效果，對我來說只會讓想像變得更大，卻不會讓工作變得更清楚。

參考網站可以提供方向，不能代替規劃

一開始看到喜歡的網站，我很自然會想：「如果我的網站也長這樣就好了。」這個想法並不錯，因為參考案例可以幫助團隊討論視覺方向；但它只能回答一部分問題。

它可以讓我描述自己喜歡大圖、留白、卡片或數據區塊，卻不能直接告訴我：訪客第一眼應該先看到什麼、下一步要點哪裡、不同角色看到的內容是否一樣，也不能保證別人的版型適合自己的資料量與維護方式。

所以我後來會把「我喜歡這個網站」改寫成幾個比較能工作的問題：

  1. 這個畫面最希望訪客完成哪一個動作？
  2. 訪客完成動作時，需要先看懂哪些資料？
  3. 這些資料由誰建立、更新與確認？
  4. 如果資料還沒有、填錯或狀態異常，畫面要怎麼說明？
  5. 手機使用者、第一次來的人，以及不熟悉專業詞彙的人，能不能走完同一條路？

我不一定能立刻回答所有問題，但只要能把問題列出來，就能知道自己目前缺的是資料、決策，還是需要請教別人的技術。這比一直要求自己「先想出完整網站」更實際。

新手也能先交付的，不是美感，而是可討論的骨架

我現在回頭看，自己當時能提供的工作價值，不是直接做出設計稿，而是先把模糊的想法整理成別人可以接手的骨架。

原本容易說出口的話 可以交付的工作內容
我希望網站漂亮、專業一點 寫出參考案例的版型特徵，以及不希望出現的呈現方式
我希望民眾一進來就看懂 指定第一眼要理解的資訊與完成的下一個動作
我希望廠商操作簡單 畫出登入、查看待辦、填寫、送出與失敗處理的路徑
我希望資料可以公開 標出資料來源、審核狀態、更新時間與前台呈現位置
我希望手機也能使用 先決定手機版保留哪些資訊，以及哪些操作不能被省略

這些內容還不是完整需求規格，也不代表方案已經可行；它們比較像是讓設計師、工程師與業務一起討論的共同語言。對新手來說，先把「我想要什麼」變成「使用者要完成什麼、系統要提供什麼、團隊要確認什麼」，就是一個很實際的進步。

這份工作經驗還可以怎麼延伸

如果要把這次經驗繼續發展下去，我覺得可以往四個方向補強：

  1. 把全貌畫出來。 先整理現況與目標，列出內容分類、使用角色與主要頁面，不急著處理視覺細節。
  2. 把路徑走一遍。 各挑一個民眾與內部使用者的任務，寫出從進站到完成的每一步，並補上找不到資料、權限不足與送出失敗的例外路徑。
  3. 把資料生命週期補齊。 確認資料如何產生、檢查、修正、發布與更新，避免前台畫出漂亮的數據，後台卻沒有可靠的來源。
  4. 把假設變成小型驗證。 不先投入完整開發，可以用幾張線框圖或一條可點擊的原型，請少量使用者走一次，再記錄他們在哪裡卡住。

這些延伸讓我重新理解「新手」的意思。新手不是完全不能參與，而是要知道哪些事情自己可以先整理，哪些事情必須標成假設，哪些決定需要交給有經驗的人共同確認。

先把這份紀錄放回正確位置

原始材料裡有不少具體的工具建議、操作步驟與程式碼。那些內容是當時為了把想法往前推而產生的草案，不等於已經測試過的方案，也不等於目前要照做的指示。

我真正想留下的不是某個平台的操作方式，而是三個判斷：

  1. 資料型官網不一定要把資料本身變有趣，才有機會做推廣。
  2. 改版亮點如果只用文字介紹，很容易停留在「知道有這個功能」，沒有變成「我會使用這個功能」。
  3. 網頁遊戲的價值，必須用實際的使用行為驗證，不能只用「看起來很好玩」推論有效。

問題不在資料庫無聊，而在亮點沒有被使用

資料型官網通常有搜尋、篩選、分類、快捷入口、資料下載或行動版介面等改版內容。這些功能對熟悉網站的人可能很重要，但對一般訪客來說，未必值得特別花時間研究。

如果宣傳文案只寫「介面更新」「搜尋更精準」「新增專區」，訪客只是在閱讀一串功能清單。他知道網站改過了，卻不一定知道自己什麼時候會用到這些改變。

因此，遊戲化構想的核心不是把官網做成遊戲，而是替訪客安排一個很短的使用理由：

為了解決一個小任務，親手走過新版網站的一段動線。

這個任務可以是找到某個資料、用條件篩選出一項結果，或在手機上完成原本不容易找到的操作。遊戲只是入口，真正要留下的是訪客對新動線的記憶。

把改版亮點翻譯成任務

一個好用的轉換方式，是先列出改版亮點，再問「玩家必須做什麼，才會自然用到它？」而不是先決定要做哪一種遊戲。

改版亮點 任務化的做法 玩家實際學到的事
搜尋或篩選變得更完整 給一個需要設定條件才能解開的線索 知道搜尋入口與篩選方式
導覽、分類或快捷入口重整 要玩家在新版架構中找到指定服務 記住內容被放在哪個區域
行動版閱讀與操作改善 設計一個只能或適合用手機完成的小任務 感受到手機版的操作差異
新增專區或資料服務 把它設定成任務中的關鍵地點 知道這個專區何時值得回來使用

這裡有一個重要界線：答案不應該只是藏在頁面某個角落，逼玩家靠眼力尋找。若任務最後只變成「找出一串字」，玩家可能記住的是彩蛋位置，而不是網站功能。比較好的任務應該讓「使用功能本身」就是解題過程。

三種可能的包裝方式

尋寶：適合熟悉網站結構

在幾個真實頁面或模擬頁面中放置線索，玩家依序找到服務入口、分類或小圖示。這種方式容易理解，也適合把導覽列、熱門服務與新專區串成一條路線。

它的風險是很容易退化成找不同或點擊彩蛋。如果玩家不需要閱讀頁面、不需要使用搜尋，也不需要理解內容，對官網改版的幫助就有限。

情境任務：適合示範流程價值

給玩家一個生活或工作情境，例如「需要在短時間內找到一份公開資料」，再讓他用新版官網完成查找。這比直接問「新版增加了什麼功能」更接近真實使用，也比較能說明改版到底省下了什麼阻力。

這種包裝需要控制情境的難度。故事可以有一點趣味，但不能讓玩家花更多時間理解角色、背景與規則，反而忘記原本要學的是網站操作。

單人探索：適合展示視覺與動線

另一個延伸方向，是把官網截圖或抽象化的頁面做成一張地圖，讓玩家操作角色走到不同地點，再點開任務或連到真實網站。這種形式的記憶點比較強，也能承載多個任務。

但它的成本不只在程式。背景圖需要更新，互動位置需要重新校準，手機操作需要測試，截圖上的文字也不一定能被輔助技術讀取。它適合做概念展示或短期活動，不應直接被當成官網的替代介面。

這樣的網頁有沒有用？

我的結論是：有可能有用，但它的用途是引導熟悉與活動推廣，不是取代網站本身。

目的 適合程度 原因
讓訪客知道新版網站的入口與動線 高 任務可以讓訪客實際走過一次流程
讓訪客理解一個新功能怎麼解決問題 中高 情境設計與真實操作可以互相支撐
用遊戲解釋大量政策或資料內容 中低 遊戲會增加理解層，未必能取代清楚的內容設計
修補原本不好用的網站 低 遊戲可能掩蓋問題，卻沒有改善核心使用性
長期維護成另一個正式服務入口 低 官網一改版，遊戲地圖、任務與連結都可能失效

所以判斷值不值得做時，不能只問「遊戲好不好玩」，而要問：

  • 這次改版是否有兩、三個希望訪客親手使用的亮點？
  • 每個任務能否對應到一個真實的網站行為？
  • 活動結束後，訪客是否仍知道要回哪個正式入口？
  • 誰負責在官網變更後更新任務、連結與畫面？
  • 是否有不玩遊戲也能取得同樣資訊的清楚路徑？

如果這些問題沒有答案，遊戲很可能只會帶來一次性的瀏覽量，卻沒有留下可重複的使用習慣。

低成本不代表沒有成本

原本討論過用網站製作工具、表單、互動簡報工具或靜態網站託管服務組合出原型。從技術角度看，這類方案確實可以把前期成本壓低，也能先驗證任務流程，不必一開始就開發完整的多人遊戲。

但「工具免費」不等於「活動沒有成本」。仍然要投入：

  • 把官網亮點轉成任務的企劃時間。
  • 重新確認每個連結、頁面與答案的內容維護。
  • 手機、桌機、鍵盤、觸控與不同網路狀況的測試。
  • 無障礙替代路徑與不使用遊戲者的資訊取得方式。
  • 個資、抽獎、外部服務、資安與機關審核的確認。
  • 活動結束後的下線、轉址或內容保存安排。

尤其是把正式官網的畫面截圖當成遊戲地圖，視覺上雖然容易連結兩個體驗，卻也會產生維護與理解風險：玩家看到的是靜態畫面，不一定等於當下的真實頁面；畫面中的文字可能無法直接搜尋或朗讀；官網更新後，遊戲地圖也可能迅速過期。

如果再做一次，先做最小驗證

我不會一開始就製作完整的角色移動、碰撞、背包與多關卡系統。比較適合的順序是：

1. 先選一個可觀察的行為

例如「找到某個服務入口」或「使用一次進階篩選」。不要同時宣傳所有改版亮點，否則很難知道玩家到底學會了什麼。

2. 只做三個任務

用一個簡單的任務頁、互動簡報或靜態原型，把三個任務串起來。先確認指示是否看得懂、連結是否找得到，以及玩家是否知道何時要回到正式網站。

3. 用少量真實使用者試玩

觀察玩家是否卡在故事、按鈕、網站本身或答案驗證。可以記錄完成率、放棄位置、前往正式網站的比例，以及完成後能否說出自己剛剛使用的功能。這些比單純的造訪人次更能回答「有沒有用」。

4. 再決定是否值得寫成遊戲

如果簡單原型已經能讓人理解動線，再考慮加入地圖、角色或視覺效果。如果最小版本就沒有人願意完成，增加遊戲機制通常只會讓問題更複雜。

可以重複使用的判斷清單

下次再遇到「要不要用互動網頁推廣改版」的提案，可以先檢查：

  1. 目標是什麼？ 是曝光、熟悉動線、教學，還是收集名單？不同目標不能共用同一個成功標準。
  2. 玩家要做什麼？ 任務要對應真實操作，不要只考記憶或找隱藏文字。
  3. 亮點是否足夠集中？ 先挑最值得被使用的少數功能。
  4. 正式入口在哪裡？ 遊戲結束後要把人帶回可長期使用的官方頁面。
  5. 不玩的人怎麼辦？ 所有重要資訊都要有直接、可讀、可操作的替代路徑。
  6. 誰負責維護？ 連結、截圖、題目、答案與活動規則都要有更新者。
  7. 何時算成功？ 先定義完成率、任務行為、正式網站轉換與回饋，再決定要不要擴大。
  8. 何時結束？ 短期活動要有下線日期、失效處理與內容保存方式。

未採用也值得留下來

這個構想最後沒有被採用，不代表它沒有價值。它至少幫我看見一件事：當一個網站的內容像資料庫，真正需要被設計的可能不是更多宣傳文案，而是「訪客為什麼願意開始操作」的入口。

不過，入口有趣只是第一關。遊戲能不能把人帶到正式網站、讓人完成正確操作，並在官網更新後仍然維持可信任的體驗，才是它有沒有產生工作價值的判斷基準。

我會把這個想法暫時放在「適合做小型原型，不宜直接做成長期系統」的位置：先用最小任務驗證學習效果，確認有人真的因此更會使用新版網站，再決定是否投入完整的視覺與程式開發。

一句話整理

網頁遊戲不該替不好玩的資料硬加一層娛樂，而應該把改版亮點變成訪客願意親手完成的小任務。
