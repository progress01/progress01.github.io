工作知識｜從實際抽象功能系列 03｜同一份規劃為什麼會被看成兩種工作

發表於 2026-09-17 分類於 工作知識 文章字數： 1.2k 所需閱讀時間 ≈ 1 分鐘

同一份專案規劃，執行者與主管可能正在回答不同問題：前者想著怎麼做，後者先確認值不值得做。

這不表示某一方不做事，也不代表主管只是在挑毛病。比較接近的說法是：雙方手上有不同層級的認知模型。

執行者拿到的是「如何落地」

當前期有了功能規劃、版面方向或工程清單，執行者很自然會進入這條路徑：

理解規劃 → 想辦法做出來 → 處理執行障礙 → 回報進度。

所以看到一個功能時，會先想資料怎麼放、後台怎麼做、頁面怎麼接、工程要花多少時間。這些問題都是真問題，只是比較集中在「如何完成」。

資深者看的還有「是否值得往下走」

有幾次改版經驗的人，看到同一個功能，可能同時在問：

  • 它解決誰的問題？真的有使用情境嗎？
  • 資料從哪裡來，誰能長期維護？
  • 這是誰有權決定的變更？
  • 前面的盤點、規格與確認是否已經排進時程？
  • 做下去會不會影響其他模組、流量、維運或驗收？
  • 如果工具或條件失敗，怎麼保底？
  • 會議上要拿出什麼，大家才有辦法做決定？

這不只是把「How」問得更細，而是先審查「Why、Who、What、Under which conditions」。

真正的落差不只是經驗不足

如果前期沒有把這套判斷方法轉成共同的文件、案例或清單，執行者就只能在不知道評分規準的情況下作答。直到成果出現，主管才用自己的經驗一項一項指出缺口，執行者自然會感覺像在接受口試。

這裡至少有兩種缺口：

  1. 個人經驗缺口：第一次做大型改版時，不知道前置盤點、決策邊界或影響分析本身也是工作。
  2. 組織知識傳承缺口：資深經驗存在，但沒有被制度化成團隊可取得的會前審查框架、案例庫、Checklist 或 WBS 範本。

不能因為主管看得出問題，就反推他一定曾經把判斷方法教給團隊；也不能因為執行者沒先想到，就把所有責任都歸為個人能力不足。

審查者模式與教練模式

兩種帶人的方式不同：

模式 工作方式
審查者模式 你拿成果來，我指出缺口
教練模式 開始前先說明這類工作通常檢查什麼，再陪你修正第一版

如果團隊長期只有前者，知識就會在 Review 現場被動釋出。每個新人都要先撞一次牆，下一個人還可能重新撞同一面牆。

重新看待「支援」

因此，問題不一定只是「主管有沒有幫我做事情」。我覺得更精確的問題是：

一件事情做到什麼程度，才算可以安全進入下一步？這個判準有沒有提前被團隊看見？

有些資料本來就該由 PM 主動盤點；有些工程限制要找工程師；有些既有資產的變更要由客戶或機關確認。真正需要的不是所有人都替執行者完成，而是先把資料來源、決策權與完成標準說清楚。

目前留下的工作假說

這段經驗可以先寫成一個暫定模型：

執行者採取「提案落地模型」，資深者採取「效益與風險門閥模型」；當後者沒有在前期被轉譯成共享工作標準，兩邊就會在成果 Review 時才第一次對齊。

這不是替任何一方定罪，而是讓下一步清楚：要把主管反覆使用的判斷方式拆出來，變成執行者能在事前使用的問題與產物。
