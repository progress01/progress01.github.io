簡報製作與 open-slide 2.0｜從內容、結構到上台報告的學習筆記

發表於 2026-09-07 更新於 2026-09-08 分類於 觀念與實驗 文章字數： 4.9k 所需閱讀時間 ≈ 4 分鐘

這篇學習筆記從 open-slide 2.0 視覺編輯器的分享截圖開始。最近我越來越被簡報困擾：常把時間花在排版，卻沒有先決定聽眾要記住什麼。

因此我想參考大家的簡報方法，整理內容、故事線、視覺設計與上台排練，並為 2026-09-10 的報告建立一套可以實際執行的流程。

先確認：我困擾的不是排版，而是沒有先做決策

我以前很容易一打開 PowerPoint、Google Slides 或其他簡報工具，就開始想：

  • 這頁要放幾個框？
  • 標題要用什麼字體？
  • 圖片要放左邊還是右邊？
  • 要不要加動畫？

但這些問題都太後面了。真正應該先回答的是：

報告結束時，我希望聽眾只記得哪一件事？

如果這句話還寫不出來，投影片越做越多，通常只是把不確定性搬到畫面上。簡報看起來變完整，訊息卻沒有變清楚。

目前我先把簡報拆成四個不同問題：

  1. 目的：這次是要說明、說服、報告進度，還是請大家做決定？
  2. 結構：聽眾要按照什麼順序理解？
  3. 視覺：哪些內容適合留在畫面上，哪些應該由我口頭說？
  4. 呈現：我能不能在限定時間內講完，並處理問題？

工具只能幫我加速第三項的一部分，也能改善反覆修改的效率，但不能代替前三項的判斷。

我參考大家的方法後，留下的共通原則

1. 先畫靶，再開始蒐集資料

BFA 簡報〈從一張白紙畫出專業簡報〉把前置作業放在簡報製作之前：先釐清目的、題目、對象與限制，再蒐集資料和設計故事線。

我把它改成自己可以直接使用的四句話：

我現在要對誰報告？
他們原本知道什麼？
我希望他們改變哪個理解或決定？
報告結束後，他們要做什麼？

這四句話還沒寫清楚前，不先開始排版。

2. 先做故事線，再做頁面

Duarte 對簡報故事結構的整理提供了一個很有用的觀察：簡報可以在「現在的狀況」與「可能的狀況」之間移動，最後讓聽眾抵達一個新的理解或行動。

我不把它硬套成戲劇，而是先轉成報告語言：

現在發生什麼 → 為什麼值得處理 → 我看到了什麼 → 這代表什麼 → 下一步要做什麼

如果是學術或工作報告，也可以改成：

問題 → 方法 → 證據 → 解讀 → 限制與下一步

這比「找到幾個漂亮模板」更重要，因為頁面順序本身就是聽眾理解內容的路徑。

3. 一頁不要同時承擔整篇文章

BFA 的分享把簡報主體拆成一頁一到兩個重點，並強調頁與頁之間要有連結與明確的下一步理解。這讓我重新理解「資訊完整」：不是每一個資料都要塞進投影片，而是每個資料都要知道自己在故事裡負責什麼。

我先採用比較嚴格的版本：

一頁只負責一個主要訊息，其他內容只用來支持它。

每張投影片製作前，先寫一個完整句子的標題，例如：

  • 不寫「研究結果」，改寫成「使用者最常在第三步卡住」。
  • 不寫「分析」，改寫成「問題不是資料不足，而是判斷順序混亂」。
  • 不寫「結論」，改寫成「下一次應該先固定輸入格式」。

如果標題不能先說出結論，代表我可能還沒想清楚這頁要做什麼。

4. 投影片是視覺輔助，不是逐字稿

Garr Reynolds 的 Presentation Zen Tips把準備、設計與呈現分開看，這提醒我：投影片不是把我要講的每一句話全部打上去，而是提供觀眾理解的視覺線索，讓我把剩下的脈絡講出來。

因此我會把內容分成兩層：

  • 畫面層：標題、關鍵字、圖表、關係、數字與必要的證據。
  • 講者層：例子、轉場、補充解釋、可能被問到的細節。

如果一張投影片只有把講稿縮小塞進去，觀眾就要同時讀、聽、理解，講者也容易被自己的文字綁住。

截圖中的 open-slide 2.0，對我真正有用的是什麼

從截圖看起來，open-slide 2.0 的重點不只是「用 AI 生一份簡報」，而是把投影片當成可以持續修改的視覺程式，並把視覺編輯器放進這個流程裡。

依照官方 GitHub 與文件，目前值得記錄的能力有幾個：

1. 投影片是 React 元件，不是被鎖死的模板

open-slide 使用 React 來描述投影片，每頁放在固定的 1920 × 1080 畫布中。這讓 agent 可以直接修改頁面結構、文字、樣式與視覺元件，也讓投影片可以像程式碼一樣被版本控制。

這種方式適合我想快速修改「整組頁面」的時候，例如：

  • 把所有頁面的標題層級重新整理。
  • 統一色彩、留白與字體比例。
  • 把一組重複的卡片換成時間線。
  • 對照講述順序，重排整份 deck。

2. Visual editor 解決的是微調，不是內容決策

官方的 Inspector 文件描述了視覺編輯器的做法：點選畫面上的元素後，可以調整文字、字體、字重、字級、字距、顏色與圖片來源，最後再儲存回檔案。

這對我最有價值的地方，是不用為了改一個標題大小而一直猜 JSX 中是哪個元素。但它不會替我回答：

這個標題是不是根本不該存在？

所以我應該先用內容與故事線決定「留不留」，再用視覺編輯器處理「怎麼呈現」。

3. Comment → agent 修改，形成可重複的迭代循環

open-slide 也支援在畫面元素上留下註解，再由 agent 依照註解修改原始碼。這個流程比只對 agent 說「第三頁不好看」更精準，因為註解可以附著在實際被選取的元素上。

我目前理解的循環是：

先產出 → 實際看畫面 → 點選問題 → 留下具體註解 → agent 修改 → 再看一次

這也提醒我，簡報不是一次生成的檔案，而是一個需要觀看、講述和修正的工作物。

4. Presenter mode 與輸出格式仍要先驗證

官方 GitHub 提到 open-slide 有全螢幕播放、講者模式、目前／下一頁預覽、講者備註與計時器，也能輸出靜態 HTML 和 PDF。

但如果週四的場合明確要求 PowerPoint .pptx，就不能只因為畫面很漂亮便假設它可以直接取代 PowerPoint。我要先確認報告現場能否使用 HTML 或 PDF；如果不行，就要及早改用能交付 .pptx 的流程，或把 open-slide 當成內容與視覺草稿工具。

我想採用的簡報製作流程

第 0 步：寫一張簡報任務卡

在開任何簡報工具之前，先寫下：

如果這張任務卡寫不出來，就先不要要求工具生成完整 deck。

第 1 步：先用卡片排故事線

先不用排版，每張卡片只寫四件事：

欄位 要寫什麼
頁面主旨 這頁希望觀眾理解的完整句子
支持證據 數字、例子、截圖、引用或觀察
畫面形式 圖表、流程、比較、時間線或一句話
口頭補充 只有我上台時需要講的脈絡

先把卡片排順，再決定哪幾張合併、哪幾張刪掉。

第 2 步：建立最小視覺系統

我不再每頁重新做設計，而是先固定：

  • 一個背景色與一個主要文字色。
  • 一個強調色，只有在真的需要注意時才使用。
  • 兩到三個文字層級。
  • 一種主要版型，以及一到兩種變化版型。
  • 圖表、圖片與文字的固定對齊方式。

視覺一致不是讓每頁長得一樣，而是讓觀眾不用重新學習介面，就能把注意力放回內容。

第 3 步：再讓工具加速實作

如果使用 open-slide，我目前會這樣分工：

  1. 我先提供任務卡、故事線、受眾、時間與視覺方向。
  2. agent 先做一版內容與頁面結構。
  3. 我用簡報模式完整看一次，不在第一眼就修改細節。
  4. 把問題分成內容問題、順序問題、視覺問題與現場問題。
  5. 能用一句話描述的視覺問題，透過 Inspector 或 comment 回傳。
  6. 修改後重新從頭播放，而不是只看被改的那一頁。

這樣可以避免把 agent 當成只會幫我換顏色的排版工，也避免我只看到局部漂亮，卻沒有檢查整份簡報能不能被講完。

這週四報告前的最小計畫

這份計畫建立於 2026-09-07，預計 2026-09-10（週四）再次上台。時間有限時，我先不追求完整的設計系統，而是先完成一份可以講清楚的最小 deck。

2026-09-07：先定一句話與六張骨架

先完成這六張，不先加動畫：

  1. 開場：今天只希望大家記住什麼？
  2. 問題：為什麼這個題目值得花時間？
  3. 背景或方法：我用什麼方式理解它？
  4. 證據或案例：哪個資料最能支持我的說法？
  5. 解讀：這個證據代表什麼？
  6. 結尾：所以接下來要做什麼？

如果報告是研究型題目，第 3、4、5 張可以對應研究方法、結果、討論；如果是工作報告，則可以對應現況、處理方式、成果與下一步。

2026-09-08：只補必要內容

每頁完成一個結論式標題，並只留下支持這個標題的內容。任何「可能有用但不影響主線」的資料先移到附錄，不要因為捨不得而塞進主體。

2026-09-09：至少完整講兩遍

排練時不只看畫面，要記錄：

  • 是否超過時間。
  • 哪一頁需要我讀字才能講下去。
  • 哪一頁我自己也不知道重點在哪裡。
  • 哪一頁轉場最突兀。
  • 聽眾可能在哪裡追問定義、證據或限制。

完成後輸出 PDF，並準備一份不依賴網路的備份。若使用 open-slide，還要確認現場能否開啟 HTML 或使用 PDF 播放。

2026-09-10：上台時先講主旨

不要用「不好意思我做得不太好」開場，也不要一開始就把所有背景資料倒給聽眾。先說明今天的主旨，再帶他們走過問題、證據與結論。

我希望自己最後採用的開場格式是：

今天我想說明的是＿＿＿＿。
這件事重要，是因為＿＿＿＿。
我會用＿＿＿＿個部分帶大家看，最後回到＿＿＿＿。

目前的暫時結論

這次看 open-slide 2.0，真正讓我有感的不是它可以把投影片做得多漂亮，而是它把「做簡報」變成一個可以反覆觀看、標記、修改和版本化的工作流程。

但工具越方便，越不能把內容決策交出去。對我來說，目前最重要的順序是：

先決定聽眾要帶走什麼，再安排故事線；先完成能講的版本，再處理視覺；先完整排練，再追求漂亮。

週四以前，我不把目標訂成做出一份看起來像專業設計師的簡報，而是做出一份我知道每一頁為什麼存在、能在時間內講完、聽眾聽完知道下一步的簡報。

參考來源與我從中採用的部分

  1. open-slide GitHub：確認 agent-native、React 投影片、1920 × 1080 畫布、present mode、HTML／PDF 輸出與專案結構。
  2. open-slide 官方網站：了解從 init、prompt、edit 到 comment／apply 的整體工作流程。
  3. open-slide Inspector 文件：確認視覺編輯器、元素選取、儲存與 comment 的實際方式。
  4. open-slide Skills Overview：了解 /create-slide、/slide-authoring、/apply-comments 與 workspace 規則如何協作。
  5. silenceper：open-slide: A Slide Framework Built for AI Agents：參考其他人如何把 open-slide 理解成「可執行、可迭代、可版本控制的簡報程式」，而不只是一次性的 AI 產檔工具。
