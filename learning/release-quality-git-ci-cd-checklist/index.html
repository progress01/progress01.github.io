發布品質｜Git、CI/CD 與 Release Checklist｜學習筆記

發表於 2026-09-04 分類於 觀念與實驗 文章字數： 2.1k 所需閱讀時間 ≈ 2 分鐘

這篇是「網站品質與軟體測試」系列的第四階段。前面的測試如果只存在自己的電腦裡，還沒有真正接到團隊工作；這一階段要理解版本、環境、測試報告與發布判斷如何連成一個可交接的流程。

系列索引：從需求到上線驗證的學習路徑

資料狀態：建立發布品質框架，尚未完成 CI 練習專案

本單元一定要會

  • 能用 Git status、diff、add、commit、branch、switch、push、pull 與 merge 保留變更脈絡。
  • 能描述測試環境、依賴、環境變數與本機／CI 差異。
  • 能讓一種 CI 平台在 push 後安裝依賴並執行測試。
  • 能讀懂一次成功與一次失敗的測試結果，並建立功能、內容、連結、無障礙、響應式與資料檢查的 Release Checklist。
  • 能說明上線後要觀察什麼，以及問題發生時如何回報或回復。

本單元先不學

Appium、Maestro、Jenkins、Docker、複雜部署架構與多平台 CI 先不加入；這一輪只選一種 CI 平台把閉環跑過一次。

過關條件

交付一個有清楚 commit 歷史的練習 repository：push 後會自動跑測試，README 能說明失敗排查方式，並附上去識別化 Release Checklist。只會在本機手動執行，不算完成本單元。

這一階段的核心問題

我要從：

逐步理解成：

CI/CD 不是一個很大的口號，而是把這些步驟變成團隊能重複、能追蹤的流程。

Git：先學會保留變更脈絡

第一輪先掌握：

練習時直接使用 Web 自動化測試專案：先建立初始版本，再新增測試、查看差異、建立分支、合併變更。每次 commit 應該能讓人看懂「這次改了什麼」，不要把所有修改都塞進一個沒有意義的提交。

基本環境能力

QA 不必一開始研究作業系統核心，但要能在測試環境中自我排查：

  • 目前在哪個目錄、有哪些檔案與設定。
  • Python 與套件版本是否符合專案要求。
  • 環境變數是否存在，敏感值是否被安全保存。
  • 測試程序是否仍在執行、失敗紀錄放在哪裡。
  • 本機成功、CI 失敗時，兩邊的瀏覽器、依賴與資料是否一致。

這些基本能力的目的，是讓問題描述不只停在「我的電腦可以」。

一個最小 CI 練習

先設計最小目標：每次 push 時，系統自動完成以下工作：

  1. 建立指定的 Python 環境。
  2. 安裝專案依賴與瀏覽器測試需要的元件。
  3. 執行一組穩定的 Pytest／Playwright 測試。
  4. 在失敗時保留測試輸出或報告。
  5. 顯示成功或失敗，讓團隊知道這次變更是否需要處理。

第一輪不必同時學 Jenkins、GitLab CI 與 GitHub Actions；先選一種平台，把完整流程跑過一次即可。

Release Checklist 的分層

我希望最後留下的檢查表，不是「全部都看過」的口號，而是能指出檢查範圍與證據：

層次 例子 判斷證據
功能 主要流程、錯誤處理、權限與資料保存 Test Case 結果、截圖或紀錄
內容與結構 文字、連結、表格、圖片與附件 前台頁面、HTML 或內容檢查結果
使用情境 手機／桌機、不同狀態、操作中斷與恢復 情境紀錄與裝置／瀏覽器資訊
品質風險 無障礙、效能、資安或第三方服務 對應檢查結果與已知限制
發布後 監測、錯誤回報、回復方式與負責人 監測項目、聯絡窗口與處理紀錄

每個專案不一定都要有相同深度，但應該清楚知道哪些已檢查、哪些未檢查、哪些風險被接受，以及誰做最後決定。

上線不是「所有測試都 Pass」

發布判斷通常還要一起看：

  • 目前版本改了什麼，影響範圍多大？
  • 高風險案例是否已執行？
  • 尚未修正的問題是否有明確影響與接受者？
  • 是否有回復版本、監測與上線後處理方式？
  • 測試環境與正式環境的差異，是否可能讓結果失真？

我需要學會的是提供品質資訊與風險，不是單獨替整個團隊宣布「可以上線」。

這篇的實作作業

  1. 把 Web 自動化練習專案建立 Git repository。
  2. 用至少兩個有意義的 commit 記錄變更，並練習分支與差異檢查。
  3. 選一個 CI 平台，讓測試在 push 後自動執行。
  4. 保留一次成功與一次失敗的測試結果，說明失敗原因與處理方式。
  5. 建立一份去識別化的 Release Checklist，列出已檢查、未檢查與已知限制。

核心之後的延伸

Appium、Maestro 與 Jenkins 暫時不列入第一輪必修。等 Web 測試、版本控制與 CI 能完整跑過一次，再選一個 Android sample app 做最小 UI 自動化；屆時要重新學習行動裝置、driver、測試資料與執行環境的差異。

還沒回答的問題

  • 測試失敗時，誰負責判斷是阻擋發布的問題？
  • 測試報告要保留多久，才能支援後續追蹤與稽核？
  • 正式環境不能直接測試時，如何建立足夠可信的替代證據？
  • 上線後的監測，怎麼和上線前的測試案例互相補足？
