網站品質與軟體測試｜42 天鐵人挑戰：從需求到上線驗證｜學習筆記

發表於 2026-09-04 分類於 觀念與實驗 文章字數： 6.5k 所需閱讀時間 ≈ 6 分鐘

這是一個以「我想正式學會怎麼判斷網站能不能安心上線」為核心的學習系列。它不是把自己包裝成已經具備完整 QA 經驗，而是把目前的政府網站專案、網站檢核、問題追蹤與 Python 應用，逐步接到較完整的品質工程流程。

系列來源：使用者提供的 HyRead QA 職缺與網站品質學習對話整理

資料狀態：建立 42 天挑戰，尚未完成各階段實作

這份筆記是自己的課程設計與問題地圖，不是正式證照教材。後續遇到標準、工具或流程的細節，仍要回到官方文件、實際專案與可重現的測試結果核對。

我真正想學的是什麼

目前最重要的問題不是「我要不要立刻轉職 QA」，而是：

一個網站從做完到可以上線，中間要用什麼方法取得足夠的品質證據？

我過去比較常從三個位置看事情：

  • 使用者／圖資：使用者想完成什麼，資訊怎麼被找到與使用。
  • PM／維運：需求怎麼整理、問題怎麼追蹤、不同角色怎麼協作。
  • 品質／工程：怎麼證明功能符合預期，以及一次修改沒有讓其他地方壞掉。

這個系列要補的是第三個角度，但不把前兩個丟掉。品質判斷應該能回到使用者情境，也要能被團隊討論、執行與留下證據。

一條完整的網站品質流程

先把「我操作看看」改寫成一條可以檢查的流程：

這條線上的每個名詞，都要能用一個實際例子說明，而不是只記住英文名稱。

系列地圖

第一階段：測試基本功

對應筆記：測試基本功：User Story、Test Case 與 Bug Report

學習重點：

  • User Story 與 Acceptance Criteria。
  • Test Scenario、Test Case 與 Test Plan 的差異。
  • Bug Report 應包含的重現條件、預期結果與實際結果。
  • Retest、Regression Test 與 Exploratory Testing。

預計產出：一份功能 Test Plan、10–20 個 Test Cases、2 個去識別化 Bug Reports，以及修正驗證紀錄。

第二階段：測試設計

對應筆記：測試設計：等價類別、邊界值與風險導向測試

學習重點：

  • 等價類別與邊界值分析。
  • 決策表與狀態轉換。
  • 探索式測試與例外情境。
  • 依影響程度、發生可能性與使用頻率排序測試風險。

預計產出：以電子閱讀服務為情境，針對登入、搜尋、閱讀器、書籤與閱讀進度等功能，建立約 30 個有理由的測試案例。

第三階段：Web 自動化測試

對應筆記：Web 自動化測試：Python、Pytest 與 Playwright

學習重點：

  • 用 Python、Pytest 與 Playwright 執行瀏覽器測試。
  • Locator、操作、Assertion 與測試資料。
  • Fixture、參數化、失敗截圖與 Trace。
  • Page Object Model 與可維護的測試專案結構。

預計產出：至少 5 個能實際執行的 Web 自動化測試，並把其中一部分對應回第一、二階段的手動案例。

第四階段：發布品質

對應筆記：發布品質：Git、CI/CD 與 Release Checklist

學習重點：

  • Git 的基本分支、提交與差異檢查。
  • 測試環境、環境變數與基本 Linux 操作。
  • CI/CD 如何在 push 或合併後自動執行測試。
  • Test Report、Release Checklist 與上線後觀察。

預計產出：一個能在版本更新後自動執行測試的練習專案，以及一份自己的網站上線檢查表。

核心之後：App 測試

Appium、Maestro 與 Jenkins 先不列入第一輪核心。等 Web 測試、測試設計與 CI 流程能跑過一次，再選一個 Android sample app 做最小實作：啟動、定位元件、點擊、驗證結果。這樣可以分辨「真的想學行動測試」和「只是被職缺上的工具清單追著跑」。

42 天鐵人挑戰

42 天後的「會」是什麼

這不是 42 天學會所有 QA，也不是 42 天保證轉職。這一輪的完成定義是：

  1. 能用自己的話解釋核心概念，而不是只背英文名稱。
  2. 能在一個不含工作機密的練習功能上實際執行。
  3. 能留下別人看得懂、可以重做或檢查的產物。
  4. 能說出方法的限制，知道什麼情況不能只靠這個方法下結論。

六個單元的必會範圍

固定規則：用來防止發散

  1. 一個練習產品：全程只用同一個電子閱讀服務情境；自動化若需換公開 Demo，只換測試對象，不新增產品功能。
  2. 一個主要工具鏈：Python、Pytest、Playwright、Git 與一種 CI 平台。看到其他工具先放停車場。
  3. 一日一產物：每天最多一個主要產物；不要同時改筆記、履歷、作品集與工具環境。
  4. 卡住先縮小：同一問題超過 30 分鐘，先記錄錯誤、嘗試與下一步，改做當日較小的部分。
  5. 不補課式爆量：漏一天就順延，不用隔天讀兩倍；挑戰目標是建立可持續節奏。
  6. 完成才擴張：單元檢查日沒過，就只補該單元，不提前研究下一個工具。

遇到新知時的分流規則

學習前不知道的事情，不代表都要立刻加入課表。每次遇到新名詞、新工具或新的疑問，先用下面四類分流：

類別 判斷問題 現在怎麼處理
A. 必要前置 沒有它，今天的單元是否無法完成？ 只補最小必要知識，並替換一個原定任務，不增加總量
B. 當前有幫助 它能讓目前產物更可靠，但沒有它也能先完成？ 限時 30–60 分鐘做小補充，完成後回主線
C. 之後會用 它有價值，但不影響目前過關嗎？ 記入停車場，寫下觸發條件，不在今天展開
D. 純粹好奇 只是覺得有趣，與本單元產物沒有直接關係？ 只記一句，不搜尋、不開新專案

最重要的規則是：新知若真的必要，只能替換任務，不能無限加課。 例如今天原本要寫 10 個案例，卻發現必須先懂一個測試概念，就把其中一個延伸案例換成 30 分鐘的前置理解，並記錄為什麼換，不把第 11 個任務加進來。

進度不要只看「第幾天」

42 天是時間框架，不是能力百分比。每個必會項目都用四層證據記錄：

  1. 接觸過：看過資料或聽過說明。
  2. 說得出：能用自己的例子解釋用途與限制。
  3. 做得到：不照著逐步複製，能完成一次練習。
  4. 留得下：產物可重做、可檢查，也能說明為什麼這樣做。

只有到第 3 層，才算「會操作」；到第 4 層，才算這一輪的單元過關。若只是讀完文章，進度可以記成「接觸過」，不要提前標成完成。

每週檢查日只更新一張小表，不重寫整份課表：

單元 目前層級 已有證據 下一個最小行動 是否需要改路徑
例：測試設計 接觸過／說得出／做得到／留得下 連結到檔案或段落 補一個邊界值案例 是／否，附原因

路徑變更要留下紀錄

每次真的修改課表，只記五件事：

這讓「學了才知道」變成可管理的發現紀錄。只有在單元檢查日，或遇到 A 類必要前置時改動主線；其他新知留在停車場，不要每天重新排課。

學習停車場

先記下但不在 42 天內展開：Appium、Maestro、Jenkins、API 測試、效能測試、資安測試、Docker、JavaScript／TypeScript、ISTQB 證照、測試管理平台，以及把工作內部文件整理成公開作品。Day 42 再依興趣與實際職缺決定下一輪，不在中途插隊。

每日固定節奏與紀錄格式

每次約 30–45 分鐘；週末或檢查日可用 60–90 分鐘，但仍以一個產物為上限。建議固定分成：5 分鐘回想、20 分鐘學習、15 分鐘實作、5 分鐘紀錄。

每天只留下四行：

每篇後續筆記也先回答三個問題：

  1. 這個方法要解決什麼問題？
  2. 我留下了什麼可以重現或檢查的證據？
  3. 這個方法在哪些情況下不能直接下結論？

進度狀態可使用：未開始、接觸中、實作中、待驗證、已過關、暫停。這些是學習紀錄用的細部狀態；閱讀台的 state: learning 仍代表這個主題保留在永久 archive，不需要因為某個單元完成就刪除或搬移。

英文伴走軌：碎碎念先行，喜歡再成文

英文不另外開一套高壓課程，而是搭在現在的 QA 主線旁邊。這樣可以讓英文和真正正在學的內容連在一起，也不需要每天在 QA、英文、休息之間重新分配力氣。

碎碎念適合放什麼

  • 今天遇到的一個英文詞或短句，例如 expected result、reproduce、blocked。
  • 讀文件時只看懂的一小段，或一個還不確定的用法。
  • 用很簡單的英文寫一行測試結果或工作感受。
  • 今天有學習，但很累，只留下「我今天碰到什麼」的紀錄。

碎碎念不需要完整、不需要像文章，也不要求一次解決文法。它的任務只是保存接觸痕跡，讓之後有材料可以回看。

什麼時候升級成文章

符合下列任一情況，再考慮寫成文章：

  1. 同一個英文主題在碎碎念出現至少三次。
  2. 我真的喜歡這個主題，之後會想再次閱讀或整理。
  3. 已經能用自己的話說明意思，並找到至少一個實際例子。
  4. 這個內容對 QA 主線、工作或生活有長期參考價值。

沒有達到條件時，留在碎碎念就已經完成，不需要為了「看起來完整」硬寫文章。

英文伴走軌的能量版本

  • 很累：只看一個詞，或把今天遇到的英文貼進碎碎念；3 分鐘也算完成。
  • 普通：讀一小段目前單元相關的文件，記下 1–3 個詞。
  • 有精神：用英文寫 3–5 句測試結果、Bug 摘要或 README 內容。
  • 需要休息：不做英文，也不補課；休息本身是維持這條路徑的一部分。

英文的進度先用「看得懂 → 說得出大意 → 能在情境中使用 → 能自己留下簡單紀錄」觀察，不用用背了幾個單字計算。碎碎念是日常紀錄，學習文章才是經過挑選、整理與沉澱的長期 archive。

目前的自我定位

我可以把過去的經驗說成：

目前從事政府網站專案相關工作，接觸網站檢核、問題追蹤、資料整理及部分自動化工具應用；現在開始系統性學習軟體測試與品質管理方法。

這比直接宣稱自己已經熟悉完整 QA 流程準確。這個草稿夾的作用，是把「接觸過」逐步轉成「能解釋、能實作、能留下證據」。

42 天完成後再做的事

  • 依作品與實作感受，決定要深入 Web QA、測試自動化、App 測試或回到 PM 的品質協作。
  • 回頭檢查停車場，只選一個延伸主題進入下一輪。
  • 將工作經驗去識別化後，評估是否能整理成網站品質檢核作品；不直接公開客戶資料、網址、帳號或內部畫面。
