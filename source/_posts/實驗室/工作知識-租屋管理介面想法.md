我曾想替一位不喜歡密集表格的使用者，做一個能看狀態、記聯絡、直接產出報表的租屋管理介面。

<!-- more -->
這是一篇把一段尚未導入的工具構想去脈絡化後留下的紀錄。起點不是想展示一個漂亮的網頁，而是注意到有人每天要在密集的表格裡找欠款、打電話、記下處理情形，最後還要整理成固定格式的報表。我想把其中一部分工作搬到比較容易閱讀的畫面上，讓使用者少找一點、少記一點，也少在不同工具之間切換。

原始討論裡曾出現完整的 HTML、JavaScript、表格匯出與資料同步草案，但那只是低保真原型方向，不代表已完成正式系統。這篇文章保留的是需求權衡、介面想像與替人多想一步的心意，不放入真實姓名、房號、電話、金額、機關或任何個案資料。

# 這不是把表格做得更漂亮

一開始很容易把問題理解成：「把 Excel 換成網頁，看起來大一點、漂亮一點。」但如果只是換皮，使用者還是要自己找誰未繳、自己判斷哪一筆比較急、自己把紀錄整理回報表，核心負擔並沒有消失。

比較值得處理的問題是工作順序：

> 找到需要處理的對象 → 聯絡 → 記錄結果 → 更新狀態 → 產出應交付的報表

原本的表格可能同時承擔資料庫、工作清單、備忘錄與報表模板四種角色。它不是不能用，而是同一個畫面要服務太多目的，導致字變小、欄位變多，使用者每天最需要的事情反而被藏在格子裡。

所以我想做的不是全面取代表格，而是先做一個較適合日常處理的前端，最後仍保留固定格式的報表輸出。表格可以繼續扮演資料交換與交付角色，網頁則負責讓人比較容易完成每天的工作。

# 介面的第一個亮點：讓狀態變成可以移動的工作

初版構想把每一筆管理資料做成一張卡片，依照目前狀態放在不同區域。例如未處理、需要特別注意、已完成等狀態，各自成為一個可以快速掃描的區塊。

這個設計的價值不只是顏色比較醒目，而是把「我現在要處理什麼」放到畫面結構裡。當使用者完成一通電話或確認一筆款項，只要按下狀態按鈕，卡片就移到下一個區域；這比在一列資料中修改顏色、文字與備註，更接近工作本身的進度。

但看板不是萬用解法。若狀態定義不清楚，卡片只是把混亂從橫向表格搬到縱向欄位；若一筆資料可能同時有多種狀態，也不能只靠三個欄位硬塞。因此在做畫面前，必須先確認每個狀態代表的是：工作進度、資料完整度、風險程度，還是行政上要不要另行回報。這幾種概念不能混成同一個顏色。

# 第二個亮點：讓聯絡紀錄真的能被留下

表格裡的備註欄常常很窄，文字一多就被折疊、遮住，或讓使用者不想寫。租屋管理這類工作卻需要留下「何時聯絡、對方怎麼回覆、下一步是什麼」等脈絡，否則過幾天回頭看時，只剩一個模糊的狀態。

因此初版想把聯絡紀錄獨立成較大的多行輸入區，讓使用者可以用接近日常筆記的方式記下處理結果。這個改變看似只是把 input 換成 textarea，真正的意義卻是承認：紀錄不是附屬欄位，而是工作的一部分。

不過，讓人可以輸入不代表紀錄就會可用。後續仍要決定日期格式、聯絡方式、下一次追蹤時間、附件或證明如何關聯，以及多人接手時能不能看懂。若一開始把所有欄位都加上去，畫面又會回到原本密集表格的問題。

# 第三個亮點：把報表交付留在流程最後

如果日常介面變得比較容易操作，卻還要把資料一筆一筆複製回外部要求的報表，使用者仍然會覺得「最後那段最麻煩」。所以原本構想把固定格式的匯出列為核心流程之一：網頁使用容易理解的欄位，輸出時再把資料映射到交付需要的欄位順序與文字。

這裡的重點不是「一鍵」這個宣傳詞，而是把資料模型與交付格式對接起來。當使用者在介面上標記某筆資料需要另行處理，匯出的報表也應該能保留這個判斷；當聯絡紀錄有換行或較長內容，輸出後也要確認沒有遺失或變得無法閱讀。

這個功能同時是最需要小心的地方。報表格式可能變動，欄位名稱可能有正式定義，匯出內容也可能涉及個資或行政責任。原型可以先用假資料驗證欄位對照，但不能因為瀏覽器成功下載檔案，就宣稱已符合正式交付規範。

# 手機與電腦不一定要做同一件事

討論中也出現一個很實際的問題：如果手機與電腦的介面差異太大，使用者會不會覺得自己在學兩套系統？

我後來比較能接受的答案，不是要求所有裝置都擁有完全相同的功能，而是讓它們共享同一套視覺語言，再清楚分配任務角色：

- **手機或平板**：查看今天優先處理的項目、撥打電話、快速留下聯絡紀錄。
- **電腦**：檢查完整資料、處理較長的備註、確認狀態，最後匯出報表。

這樣做的前提是資料真的能同步，而且兩邊的狀態、欄位與按鈕名稱要保持一致。若同步還沒解決，就不應把「手機先記、電腦再匯出」寫成已完成的流程，只能把它當成下一階段的假設。

# 複雜不是問題，讓使用者承擔所有複雜才是

我是一個喜歡把問題拆得很細的人，也不希望「簡化」最後變成把重要差異刪掉。這個小專案讓我重新思考：簡化不必然等於鈍化，可能是把複雜保留在比較適合處理它的地方。

底層仍然可以有完整的資料結構、狀態轉移、欄位對照、匯出規則與例外處理；表層則只在當下顯示使用者需要做的下一步。真正的設計工作不是消滅複雜，而是決定哪些複雜由系統承擔，哪些判斷必須留給人，哪些資訊要在什麼時候出現。

這也是我不急著使用現成白板或筆記工具的原因之一。成熟工具可能很快就能做出看板，但仍要評估帳號、權限、學習成本、資料保存與固定格式匯出。如果最後使用者還要在不同工具之間搬資料，工具的成熟不一定等於這個情境的適合。

# 低保真原型應該拿來問什麼

原始草案雖然功能不多，卻很適合拿來討論。它不需要假裝已經能長期保存資料，也不需要先處理所有權限與例外；它的任務是讓使用者直接碰到幾個關鍵動作，再觀察哪裡順、哪裡不順。

可以用一條假資料流程來測試：

1. 找到一筆今天需要處理的資料。
2. 模擬完成一次聯絡，輸入一段紀錄。
3. 把狀態移到下一個區域。
4. 檢查畫面是否還看得出下一步。
5. 匯出一份報表，逐欄確認是否符合工作需要。

過程中不要只問「你喜不喜歡這個介面」，而要觀察使用者實際做了什麼：他是否知道先按哪裡、是否看得懂狀態、是否找得到電話與備註、是否擔心資料會不見、是否仍然想回到原本的表格。

# 把回饋翻成需求，而不是立刻加功能

使用者的回饋常常會以一句話出現，例如「還要記水電」「這筆不能放在已完成」「我想先看總額」。這些話不能直接等同於三個新按鈕，而要先判斷它改變的是哪一層：

| 回饋類型 | 先判斷什麼 | 可能的調整 |
| --- | --- | --- |
| 缺少一個資料 | 這是所有資料都需要，還是少數案例才有 | 補資料欄位、輸入位置與匯出對照 |
| 狀態放不下 | 狀態代表的概念是否混在一起 | 增加狀態、拆出旗標，或改用另一個視圖 |
| 操作太繞 | 問題在按鈕位置、步驟數，還是資訊順序 | 調整動線，不一定新增功能 |
| 想看總額或摘要 | 這是原始資料，還是由資料推導出的結果 | 增加摘要計算，不要重複儲存同一數字 |
| 不想用卡片 | 看板是否真的符合工作習慣 | 改成大字體表格或雙欄視圖，保留底層資料模型 |

這個翻譯過程比單純「聽到什麼就加什麼」更重要。它讓介面調整有依據，也讓我不會因為一個新需求，就把整個原型推翻重寫。

# 資料保存是後續，不是第一個亮點

單機原型很容易做出「按了就會變」的效果，但如果重新整理頁面後資料全部消失，它就還不能承擔正式工作。這個差距必須在文章與討論中說清楚：

- 介面操作是否直覺，是一個問題。
- 資料是否可靠保存，是另一個問題。
- 誰能看、誰能改、誰能匯出，是第三個問題。

可以先用本地假資料與手動匯出驗證操作邏輯，再決定是否需要雲端資料來源、帳號、權限、備份與多人協作。不要因為「接上資料庫」聽起來更完整，就跳過前面對使用者工作習慣的確認。

# 這個想法有沒有真正的價值？

它的亮點確實不在複雜功能，而在於替特定使用者整理一條比較不費力的路徑。如果情境具有以下特徵，客製化介面就可能值得做：

- 每天重複處理的動作很固定。
- 現有表格同時承擔太多角色，造成閱讀或記錄負擔。
- 最後有固定的報表格式，值得自動對照。
- 使用者人數不多，但每個人的操作習慣與需求很明確。
- 開發者願意長期維護欄位、規則、匯出格式與資料權限。

反過來說，如果工作流程還在快速變動、需要多人即時協作、權限與稽核要求很高，或使用者其實已經熟悉現成系統，那麼先評估成熟工具或正式系統，可能比自行維護單頁網頁更實際。

# 未完成的原型也可以是一種照顧

這個專案最後沒有成熟到能正式取代原本的工作方式，程式碼也不是文章裡最重要的成果。比較值得留下來的是：我沒有只從「我想寫什麼」出發，而是先想像另一個人每天怎麼看、怎麼記、怎麼打電話，以及最後要怎麼把事情交出去。

替人設計不一定要做出很大的系統。有時候只是把字放大、把下一步放在眼前、讓一段聯絡紀錄有地方好好留下，並且不要破壞對方最後要交付的格式。這些小地方未必足以成為產品亮點，卻可能是使用者願意繼續使用的原因。

如果未來重新做，我會先保留這份心意，再重新確認當時的工具、資料保存方式與需求是否已經改變。技術可以進化，介面也可以換，但「把複雜留在底層，替使用者少承擔一點」仍然是值得反覆檢查的方向。

# 一句話整理

> **真正的簡化不是刪掉需求的銳利，而是把複雜交給系統整理，讓使用者在當下只需要看懂下一步。**
