網站上稿出現跑版或資料異常時，我會先分清楚內容、HTML、樣式、表格與附件權限，再決定該改哪一層。

<!-- more -->

這是一篇把實際上稿問題去脈絡化後留下的排查筆記。特定網站、組織、檔案與人員資訊都已移除，只保留可以重複使用的判斷方式。

上稿看起來像是把文字貼進後台，實際上卻同時經過內容、HTML 結構、CSS 樣式、編輯器資料和檔案權限。前台一旦出現跑版、表格變形或附件行為不符預期，真正的問題不一定在文字本身。

我現在會先問：**錯的是內容，還是內容被呈現的方式？** 這個問題能避免一看到畫面不對，就在同一段文字上反覆重貼、加樣式，最後把問題弄得更難追。

## 先確認是哪一層出了問題

同一個前台異常，可能來自不同層次：

- **內容層**：文字、數字、連結或檔案本身錯誤。
- **結構層**：HTML 標籤、巢狀關係或欄列結構不完整。
- **樣式層**：CSS 權重、選擇器或響應式規則造成差異。
- **資料層**：編輯器貼入了看不見的格式、空白或舊樣式。
- **權限層**：附件的瀏覽、下載或分享設定不符合需求。

如果文字內容正確，後台預覽也正常，但公開頁面顯示不同，我會優先比較前台實際輸出的 HTML 與套用的 CSS，而不是先改文案。反過來，如果原始資料就錯了，繼續調樣式也不會讓內容變正確。

## HTML 正確，不代表畫面一定正確

HTML 決定內容的結構與語意，CSS 決定它看起來的方式。兩者必須分開檢查。

例如只想讓一句話中的幾個字變色：

```html
請先閱讀 <span class="notice">注意事項</span> 再送出。
```

這段結構只是標示樣式作用的範圍；真正的顏色仍由 `.notice` 的 CSS 決定。如果結束標籤少了，後續文字可能全部被套用同一個樣式；如果標籤完整但顏色沒出現，則要檢查前台是否有對應規則、規則是否被覆蓋，或後台是否過濾了 class。

我會依序確認：

1. 開始與結束標籤是否成對。
2. 標籤是否包住正確範圍。
3. 前台輸出的 HTML 是否和後台來源一致。
4. CSS 選擇器是否命中元素。
5. 是否有更高權重或響應式規則覆蓋樣式。

先把結構和樣式分開，才能知道該改哪裡，也比較不會用行內樣式一層層蓋住真正原因。

## 表格不是一段文字，而是一組結構化資料

從試算表、Word 或其他網頁複製表格時，除了看得到的文字，也可能帶入欄寬、字型、合併儲存格、空白段落與內嵌樣式。後台畫面看似正常，公開頁面卻可能因站台 CSS 或螢幕寬度不同而變形。

遇到表格異常，我會先判斷資料是否還可靠。

### 資料正確，只有外觀不一致

可以保留表格結構，再檢查：

- 表頭是否使用正確的欄位。
- 每一列的欄數是否一致。
- 是否存在多餘的合併儲存格或固定寬度。
- 樣式是由站台 CSS 控制，還是從來源一起貼進來。
- 手機版是否允許水平捲動或有適當的縮排方式。

### 結構已混亂

如果欄位錯位、合併關係難以辨認，或反覆清理仍殘留大量內嵌格式，直接重建通常更可靠。先把內容整理成純資料，再依正確欄列重建表格，比繼續修補不可見格式更容易驗證。

重建前要保留原始內容，並逐欄比對標題、列數、排序、單位、連結與備註。重建的目的不是讓畫面看起來乾淨而已，而是重新建立可維護的資料結構。

## 附件能看、能下載與能分享是三種不同需求

附件問題常被當成連結格式問題，其實核心通常是權限與使用流程。

- **能看**：使用者可以在瀏覽器或檢視器中閱讀。
- **能下載**：使用者可以取得檔案副本。
- **能分享**：使用者可以把存取入口交給其他人。

這三種能力不一定要同時開放。如果需求是「可線上閱讀，但不要主動提供下載」，就要先確認平台是否支援這種權限，以及它能防到什麼程度。單純把檢視網址改成直接下載網址，不只沒有解決權限問題，還可能繞過原本的使用設計。

權限敏感的內容不應靠前端按鈕或網址變形來保護。應由檔案平台、帳號權限與分享政策決定誰能存取；若平台本身無法提供需要的控制，就要回到需求端確認是否換交付方式，而不是假設畫面上沒有下載按鈕就等於檔案不能被保存。

## 一套可以重複使用的排查順序

### 1. 保留現況

先保存原文、原始碼、附件連結與異常截圖。沒有基準，就很難判斷後續修改是改善，還是製造了新的差異。

### 2. 縮小問題範圍

確認異常出現在哪個頁面、裝置、瀏覽器與登入狀態，並判斷是單筆內容還是同類頁面都受影響。

### 3. 分開檢查內容與呈現

先比對文字、數字、連結和檔案，再看 HTML 結構、CSS 與響應式行為。不要同時改內容和樣式，否則很難知道哪個變更真正有效。

### 4. 檢查貼上來源帶來的隱藏格式

來源若是 Word、試算表或其他網頁，應特別查看行內樣式、固定寬度、空白段落、合併儲存格與非預期標籤。

### 5. 單點修正，小範圍驗證

一次只改一個可驗證的原因，先在草稿或測試環境確認，再套用到其他相似內容。若問題來自共用樣式，要先評估它會影響哪些頁面。

### 6. 回到公開前台驗收

後台正確不等於使用者看到的頁面正確。至少要檢查桌面與手機寬度、公開權限、連結行為，以及未登入使用者實際看到的結果。

## 什麼時候不該繼續在後台修

如果已確認來源內容正確，而多個頁面同時出現相同異常，問題可能在共用模板或 CSS；如果權限設定正確，公開連結仍不符合需求，可能是平台能力限制。這時應把可重現步驟、頁面範圍、預期結果與實際結果整理後交給對應的開發或平台管理人員。

另外，只要調整可能影響整站樣式、改變附件存取範圍，或涉及敏感資料，就不適合靠試錯直接改正式環境。先確認影響範圍與復原方式，比急著讓單一畫面看起來正常更重要。

## 結語

可靠的上稿不只是把內容放上網站，而是知道內容會經過哪些層次，並能在出錯時找到真正的責任邊界。

> **先判斷問題屬於內容、結構、樣式、資料還是權限，再用最小修改驗證；不要讓表面的跑版掩蓋真正原因。**
