這篇是「網站品質與軟體測試」系列的第一個實作入口。我要先學會把一句模糊的需求，整理成可以執行、可以記錄、可以回頭檢查的測試工作，而不是一開始就急著學自動化工具。

**系列索引**：[從需求到上線驗證的學習路徑](../website-quality-testing-roadmap/)

<!-- more -->

> **資料狀態：建立方法與練習題，尚未完成實際案例**

## 本單元一定要會

- 能分辨 User Story、Acceptance Criteria、Test Scenario、Test Case、Test Plan、Bug Report、Retest 與 Regression Test。
- 能把一個模糊需求寫成至少 5 條可觀察的驗收條件。
- 能完成 10 個包含前置條件、步驟、預期結果與證據欄位的測試案例。
- 能寫出至少 1 份別人可以重現的 Bug Report。

### 本單元先不學

ISTQB 證照準備、測試管理平台、完整測試自動化框架與效能／資安測試先放到系列總路徑的學習停車場。

### 過關條件

找一個不含工作機密的登入或搜尋功能，讓另一個人只看你的 Test Plan 與 Test Cases，就能知道測試範圍、執行步驟與通過判斷。做不到時，先修文件，不增加工具。

## 這一階段要學會什麼

面對「使用者可以登入」這類需求，我要能繼續追問：

- 什麼條件算成功？
- 錯誤帳密、空白欄位與異常輸入怎麼處理？
- 哪些行為是使用者真的會遇到的風險？
- 測試結果要留下什麼證據，別人才能重現？

這一階段的目標不是寫出完美文件，而是建立一條基本的測試語言。

## 名詞先對齊

| 名稱 | 目前的操作型理解 | 要留下的產物 |
| --- | --- | --- |
| User Story | 從使用者角度描述想完成的事情與目的 | 一句需求與角色、目標、價值 |
| Acceptance Criteria | 判斷需求是否達成的條件 | 可檢查的成功與限制條件 |
| Test Scenario | 一個值得驗證的情境或方向 | 測試範圍清單 |
| Test Case | 包含前置條件、步驟、資料與預期結果的可執行案例 | 測試案例表 |
| Bug Report | 描述實際結果與預期不一致的問題 | 可重現的缺陷紀錄 |
| Retest | 修正後，重新檢查原本的問題是否解決 | 修正驗證結果 |
| Regression Test | 確認修改沒有破壞其他既有功能 | 受影響範圍的回歸結果 |

這些名稱不是文件格式遊戲。它們分別回答「要做什麼」「怎麼判斷」「出錯怎麼溝通」與「修好後如何建立信心」。

## 第一個練習：把需求變成測試

先用不涉及工作機密的登入功能作為練習：

**User Story**

> 身為註冊使用者，我希望輸入正確帳號與密碼後登入，以便使用需要登入的功能。

**Acceptance Criteria 初稿**

1. 輸入有效帳密並送出後，系統進入登入後頁面。
2. 輸入錯誤密碼時，系統顯示可理解的錯誤訊息，不洩漏不必要的帳號資訊。
3. 帳號或密碼為空白時，系統提示必要欄位，且不應送出無效請求。
4. 登入失敗後，使用者仍能修正資料並再次嘗試。
5. 測試結束後，帳號狀態與測試資料不應污染下一個案例。

這些條件仍然只是練習用的初稿，之後要依實際產品規格、資安要求與團隊約定確認。

## Test Case 最小欄位

第一版先不要追求複雜工具，使用表格即可：

| 欄位 | 要寫什麼 |
| --- | --- |
| ID | 穩定且容易引用的編號，例如 TC-LOGIN-001 |
| 前置條件 | 使用者狀態、瀏覽器、測試資料與環境 |
| 測試資料 | 帳號、密碼或其他輸入值；敏感資料不可直接放入公開筆記 |
| 操作步驟 | 任何人依序執行都能得到相同方向的步驟 |
| 預期結果 | 可觀察、可判斷，不寫「應該正常」 |
| 實際結果 | 執行後真實看到的結果 |
| 狀態 | Not Run、Pass、Fail、Blocked 等 |
| 證據 | 截圖、錯誤訊息、紀錄檔或重現連結 |

第一輪至少寫出：正確帳密、錯誤密碼、錯誤帳號、帳號空白、密碼空白、超長輸入、重複送出、登入失敗後重試、工作階段逾時與不同裝置／瀏覽器等情境。這張清單之後還要用測試設計方法重新檢查，不代表每一項都同樣重要。

## Bug Report 的基本結構

一份好的問題紀錄，不是只寫「登入壞了」，而是讓另一個人能在相同條件下看到同一件事：

```text
標題：在有效帳密下送出登入，頁面停留在登入頁且沒有錯誤提示
環境：測試環境、瀏覽器與版本、裝置
前置條件：使用已啟用的測試帳號
重現步驟：
1. 開啟登入頁
2. 輸入有效帳號
3. 輸入有效密碼
4. 點擊登入
預期結果：進入登入後頁面
實際結果：頁面停留在原處，無成功或錯誤訊息
影響與證據：附上截圖、時間、版本與相關紀錄
```

嚴重度、優先度與是否為真正缺陷，仍要依產品影響、發生範圍與團隊定義判斷；不能只因為自己覺得嚴重就直接替團隊下結論。

## 我需要特別避免的誤區

- 把「看起來沒問題」當成測試通過。
- 只有操作步驟，沒有明確預期結果。
- 只記錄失敗，不保存環境與證據。
- 修正後只重跑原本案例，沒有確認可能受影響的既有功能。
- 把所有想得到的情境都列進來，卻沒有依風險與使用頻率排序。
- 直接把工作上的網址、帳號、畫面或內部資料放進公開作品。

## 這篇的實作作業

選一個公開 Demo 或自己建立的簡單功能，完成：

1. 一份 User Story 與 Acceptance Criteria。
2. 一份簡短 Test Plan，寫清楚範圍、環境、限制與通過條件。
3. 10–20 個 Test Cases。
4. 2 份去識別化 Bug Reports；如果沒有真實 Bug，可以用「預期失敗情境」練習，但要標明是模擬案例。
5. 一筆 Retest 與一筆 Regression Test 紀錄。

## 還沒回答的問題

- 什麼條件下可以停止測試並建議發布？
- 測試案例的優先度要由誰決定？
- 發現問題時，如何區分需求不清、實作缺陷與環境問題？
- 一份測試文件怎麼保持足夠清楚，又不變成沒有人維護的文件堆？
